# 深度解析 Ubuntu 26.04 对 Apache systemd 服务的安全限制收紧与避坑指南

> # Ubuntu 26.04 Tightens Apache's Systemd Restrictions: An Analysis

### 文章背景与核心概要

随着 Ubuntu 26.04 长期支持版本的推进，Canonical 官方进一步收紧了核心服务的基础安全策略，在 `apache2.service` 的 systemd 单元中默认开启了严苛的沙盒限制机制。这些加固策略虽然在源头上封堵了大量提权与越权漏洞，但对于大量使用 CGI 脚本、动态 PHP 扩展或 JIT 运行时的现实业务而言，极易产生静默崩溃与权限异常。本文结合具体参数，深度剖析了各项配置的底层原理、排障难点及应对方案，并提炼出兼顾安全性与兼容性的实操配置建议。

---

## 核心概述

> ## Summary

在 Ubuntu 26.04 中，Canonical 为 `apache2.service` 引入了极其严苛的 systemd 服务单元配置文件。对于那些只在 `/var/www` 下提供静态网页文件的极简 Web 服务器而言，这些限制大概率相安无事；但对于架构稍显复杂的业务环境——比如通过 `suexec` 为不同用户执行独立 CGI 脚本的部门服务器、各类 PHP 应用程序，或是挂载了多种 Apache 扩展模块的系统——这些限制将引发严重的兼容性故障。本文将深入剖析该版本中那些令人瞩目的 systemd 限制项，指出潜在的隐患暗坑，并帮助大家甄别出哪些安全加固配置依然保持合理且实用。

> In Ubuntu 26.04, Canonical has introduced a heavily restricted `apache2.service` systemd unit file. While these restrictions are likely harmless for basic web servers serving static files from `/var/www`, they can cause significant compatibility issues for more complex setups—such as departmental servers running user CGIs via `suexec`, PHP applications, or various Apache modules. This document breaks down the eyebrow-raising systemd restrictions introduced in this release, highlights potential pitfalls, and distinguishes them from the security settings that remain sensible and practical.

---

## 1. 潜藏隐患的高风险安全限制

> ## 1. Potentially Problematic Restrictions

Apache 服务配置中新增的以下 systemd 设置，很可能会干扰非标准环境配置、动态代码执行或老旧的历史遗留脚本：

> The following systemd settings added to the Apache service file may interfere with non-standard configurations, dynamic execution, or legacy scripts:

### `PrivateTmp=true`

> ### `PrivateTmp=true`

* **实际影响**：该配置沿用自 Ubuntu 24.04，其核心作用是将 Apache 的临时文件目录与操作系统的其余部分彻底隔离。
* **分析解读**：这给日常的故障排查带来了直接挑战。例如，如果你通过 `suexec` 来运行普通用户的 CGI 脚本，管理员通过 SSH 登录服务器后，根本无法直接查看 Web 应用实际读写的 `/tmp` 和 `/var/tmp` 目录。对于非特权普通用户而言，他们更没有任何简便途径去访问这个专属于服务私有的 `/tmp` 空间。

> * **Impact:** Carried over from 24.04, this setting isolates Apache's temporary directory from the rest of the system. 
> * **Commentary:** It can cause debugging challenges. For instance, if you use `suexec` to run user CGIs, administrators logging in via SSH will not be able to see the same `/tmp` and `/var/tmp` directories used by the web application. Unprivileged users have no easy way to access a private `/tmp`.

### `LockPersonality=yes` 与 `SystemCallArchitectures=native`

> ### `LockPersonality=yes` and `SystemCallArchitectures=native`

* **实际影响**：在 64 位 x86 架构系统下，这些设置会彻底拦截老旧 32 位 x86 程序的执行，并直接触发 `SECCOMP` 过滤报错。
* **分析解读**：任何依赖老旧 32 位二进制可执行文件 (例如历史遗留的早期 CGI 脚本) 的生产环境，都必须在服务配置中剔除这些限制项。

> * **Impact:** On 64-bit x86 systems, these settings prevent old 32-bit x86 programs from running, resulting in `SECCOMP` errors.
> * **Commentary:** Environments that rely on legacy 32-bit binaries (such as older CGIs) will need to drop these restrictions.

### `DevicePolicy=closed` 与 `PrivateDevices=yes`

> ### `DevicePolicy=closed` and `PrivateDevices=yes`

* **实际影响**：直接封锁了对真实 `/dev` 设备的所有访问权限，包括通过 CGI 或 PHP 扩展模块调用的硬件安全令牌 (Hardware Token) 以及各类 GPU 设备。
* **分析解读**：虽然 `DevicePolicy=closed` 通常可以平稳运行，但往往必须去除 `PrivateDevices=yes`，因为官方文档早已明确警告该项指令可能会破坏传统应用程序的正常运行。

> * **Impact:** These block all access to real `/dev` devices, including hardware tokens and GPUs accessed via CGIs or PHP modules.
> * **Commentary:** While `DevicePolicy=closed` is generally acceptable, dropping `PrivateDevices=yes` is often necessary because the documentation explicitly warns that it can break older programs.

### `MemoryDenyWriteExecute=yes`

> ### `MemoryDenyWriteExecute=yes`

* **实际影响**：与任何需要在运行时动态生成内存代码的程序和类库完全不兼容，包括即时编译 (JIT) 执行引擎、可执行栈空间 (Executable Stacks) 以及编译器蹦床 (Compiler Trampoline) 特性。
* **分析解读**：这极易直接导致复杂的 Web 应用程序崩溃，例如部署在 Apache 之后的 PyPy (Python) 或运行 Node.js / Chrome V8 引擎的 JavaScript 运行时。

> * **Impact:** Incompatible with programs and libraries that generate dynamic runtime code, including JIT execution engines, executable stacks, and compiler trampoline features.
> * **Commentary:** This will likely break complex web application stacks, such as PyPy (Python) or Node.js/Chrome V8 JavaScript engines running behind Apache.

### `ProtectProc=invisible` 与 `ProcSubset=pid`

> ### `ProtectProc=invisible` and `ProcSubset=pid`

* **实际影响**：极大收紧了进程在 `/proc` 虚拟文件系统中的可见范围。
* **分析解读**：Linux 系统的许多关键内核 API 都是通过 `/proc/` 暴露的。限制该目录的可见性，将直接破坏那些并非极简模式的应用程序或模块 (例如 PHP 或 Python WSGI) ，因为它们往往需要读取宿主系统的状态信息 (比如读取 `/proc/cpuinfo` 来探测 CPU 指令集特性) 。

> * **Impact:** Restricts visibility in the `/proc` filesystem. 
> * **Commentary:** Linux exposes critical kernel APIs via `/proc/`. Restricting this can break non-trivial programs or modules (like PHP or Python WSGI) that rely on reading system information (such as `/proc/cpuinfo` for CPU features).

### `ProtectHome=read-only`

> ### `ProtectHome=read-only`

* **实际影响**：全面封锁针对用户家目录 (`/home`) 的写入权限。
* **分析解读**：如果你的服务架构使用了 Apache 的单用户主目录 Web 功能 (即 `public_html`) ，且其中的脚本或 PHP 程序需要在 `/home` 路径下执行写操作，该设置将导致操作直接报错中断。

> * **Impact:** Blocks write access to user home directories.
> * **Commentary:** If your setup utilizes Apache per-user web directories (`public_html`) where scripts or PHP programs need write permissions inside `/home`, this setting will cause failures.

### `RestrictNamespaces=yes`

> ### `RestrictNamespaces=yes`

* **实际影响**：严格限制 Linux 命名空间 (Namespace) 的新建与操作权限。
* **分析解读**：尽管命名空间经常是安全攻击的常见突破口，但在特定生产环境下，部分由 Apache 调起的本地应用程序或扩展模块可能确实具备创建或隔离命名空间的合理业务需求。

> * **Impact:** Limits Linux namespace creation.
> * **Commentary:** While namespaces are a frequent security vector, some local applications or modules launched via Apache may legitimately require namespace manipulation.

### `ProtectSystem=full` 与显式声明的 `ReadWritePaths`

> ### `ProtectSystem=full` with explicit `ReadWritePaths`

* **实际影响**：限制对绝大多数系统目录的写入访问，仅对 `/var/log/apache2` 和 `/var/cache/apache2/mod_cache_disk` 等白名单路径开放写权限。
* **分析解读**：这种全局写保护机制可能会与第三方扩展组件的需求产生冲突，例如某些特定 PHP 模块运行所需的本地 SQLite3 数据库文件便会因缺乏写入权限而无法工作。

> * **Impact:** Limits write access across system directories while selectively opening paths like `/var/log/apache2` and `/var/cache/apache2/mod_cache_disk`.
> * **Commentary:** This can conflict with requirements for external components, such as SQLite3 databases utilized by specific PHP modules.

### `RemoveIPC=yes`

> ### `RemoveIPC=yes`

* **实际影响**：当控制组 (cgroup) 退出时，自动销毁并清理其残留的进程间通信 (IPC) 资源对象。
* **分析解读**：在 Ubuntu 26.04 的默认预设下，该配置实际上收效甚微。因为系统的 `apache2.service` 配置文件本身并未声明 `User`、`Group` 或 `DynamicUser` 指令。此外，它对服务主 UID 之外派生出的独立子进程 (例如特定配置下的 `mod_wsgi` 运行架构) 完全不生效。

> * **Impact:** Cleans up IPC objects when a cgroup exits.
> * **Commentary:** This setting is largely ineffective in the default Ubuntu 26.04 configuration because the `apache2.service` file does not define a `User`, `Group`, or `DynamicUser`. Furthermore, it does not apply to processes spawned outside the primary UID (such as certain `mod_wsgi` configurations).

## 2. 合理且值得推荐的安全加固项

> ## 2. Sensible and Recommended Restrictions

在本次更新中，有数项新启用的安全限制表现优异，它们构建了扎实的纵深防御，且通常不会对标准 Web 服务的正常运行造成任何破坏：

> Several newly enforced settings are robust security improvements that generally do not disrupt standard operations:

```ini
KeyringMode=private
ProtectClock=yes
ProtectControlGroups=yes
ProtectHostname=yes
ProtectKernelLogs=yes
ProtectKernelModules=yes
ProtectKernelTunables=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
```

* **`RestrictSUIDSGID`**：该指令限制的是新建 setuid/setgid 二进制文件 (而非限制既有程序的执行) ，是一项非常成熟稳健的安全加固实践。
* **`ProtectControlGroups=yes`**：为进程提供 cgroup 层级结构的只读视图。这允许程序正常读取系统可用的 CPU 等硬件资源配额，同时彻底杜绝了非法修改控制组参数的可能性。
* **`ProtectKernelModules=yes`**：安全地禁止手动加载或修改内核模块，同时依然保留了标准网络协议按需隐式加载底层模块的能力。

> * **`RestrictSUIDSGID`**: Restricts the creation (rather than the execution) of setuid/setgid binaries, which is a solid security practice.
> * **`ProtectControlGroups=yes`**: Grants a read-only view of the cgroup hierarchy. This allows programs to inspect available CPU resources without modifying system constraints.
> * **`ProtectKernelModules=yes`**: Safely blocks manual kernel module manipulation while still allowing implicit kernel module loading for standard network protocols.

### 受强力保护的系统敏感路径

> ### Hardened Paths

```ini
InaccessiblePaths=/boot
InaccessiblePaths=/root
InaccessiblePaths=-/etc/sudoers
InaccessiblePaths=-/etc/sudoers.d
InaccessiblePaths=-/etc/ssh
InaccessiblePaths=-/etc/apt
InaccessiblePaths=-/etc/.git
InaccessiblePaths=-/etc/.svn
```

* **分析解读**：通过上述路径限制，系统成功隔离了核心系统目录与版本控制仓库元数据，有效防止了敏感信息泄露。系统管理员还可以根据实际业务场景进一步扩展该列表，将更多本地机密路径纳入保护范围。

> * **Commentary:** These paths successfully shield sensitive system files and version control directories from exposure. Administrators can extend this list to cover other localized sensitive paths as needed.
