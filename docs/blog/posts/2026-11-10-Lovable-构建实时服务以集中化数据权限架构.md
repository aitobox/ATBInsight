# Lovable 构建实时服务以集中化数据权限架构

### 文章背景与核心概要
在现代全栈与 AI 应用开发中，传统客户端直连数据库虽然上线初期简便，却极易造成权限难以管控和网络负载暴增等隐患。知名 AI 代码生成平台 Lovable 近日全面上线了自研的实时服务 Lovable Realtime，正式将前端监听彻底从客户端 Firestore 直连剥离，转向由 Go 语言编写的集中式实时权限与数据分发架构。这一新系统在承载超过 200 万峰值并发订阅的同时，无缝打通了 Firestore 与 Google Cloud Spanner 双数据库，并依托数据去重与增量更新机制，奇迹般削减了 97% 的网络传输负载。Lovable 在短短 40 个工作日内完成核心建设并通过影子流量零故障平滑上线，为构建兼具毫秒级实时性与严苛权限隔离的大规模企业级架构提供了极佳范例。

---

## 核心摘要：自研服务破解实时权限难题

> ## Summary

随着自研实时服务 **Lovable Realtime** 的全面部署，Lovable 成功将前端架构彻底移出了 Firestore 体系。该服务采用 Go 语言构建，旨在集中管理用户鉴权并提供高效的实时数据分发。在支撑超过 200 万峰值并发订阅的严苛场景下，这套全新架构无缝整合了来自 Firestore 与 Google Cloud Spanner 的异构数据，并在后端统一执行严密的安全权限控制。凭借高效的数据去重机制、增量差异更新 (Delta-based Updates) 以及稳妥的灰度发布策略，Lovable 在未发生任何用户侧故障或性能回退的前提下，惊人地将应用程序传输负载降低了 97%。

> Lovable successfully migrated its frontend away from Firestore with the full deployment of **Lovable Realtime**, a custom Go-based service designed to centralize authorization and real-time data delivery. Reaching over 2 million peak concurrent subscriptions, the new architecture integrates data from both Firestore and Google Cloud Spanner while applying robust, backend-enforced permissions. Through efficient deduplication, delta-based updates, and strategic rollout methods, Lovable achieved a dramatic 97% reduction in application payloads without encountering user-facing incidents or performance regressions.

## 集中化权限管控与实时数据流

> ## Centralizing Permissions and Live Data

此前，[Lovable](https://www.unite.ai/lovable-acquires-sutro-company-behind-the-slang-programming-language/) 的部分功能高度依赖浏览器端的 Firestore `onSnapshot` 监听器来获取实时数据变动。在旧架构下，浏览器会直接拉取完整的文档快照，这迫使 Firestore 的安全规则必须复刻 Go API 复杂的权限模型。这种模式给数据安全治理带来了巨大隐患：只要开发人员在文档中新增一个字段，就极易意外将敏感数据暴露给用户的浏览器端。此外，Firestore 的安全规则无法直接跨库查询 Spanner 中的数据，这也给管理通过跨域身份管理系统 (System for Cross-domain Identity Management, SCIM) 同步的企业级工作区带来了巨大的技术阻碍。

> Parts of [Lovable](https://www.unite.ai/lovable-acquires-sutro-company-behind-the-slang-programming-language/) previously relied on browser-based Firestore `onSnapshot` listeners for real-time updates. Under that legacy architecture, the browser received entire documents directly, forcing Firestore security rules to mirror the Go API's complex permissions model. This design inadvertently exposed data governance risks: simply adding a field to a document could accidentally expose sensitive data to the user's browser. Furthermore, Firestore rules could not query Spanner data, creating severe hurdles for managing enterprise workspaces synchronized through SCIM.

为了攻克这些痛点，Lovable 在 Google Kubernetes Engine (GKE) 上专门构建并运行了一套自研的 Go 微服务。该服务的核心架构具备以下四大关键特性：

> To solve these challenges, Lovable engineered a custom Go service running on Google Kubernetes Engine (GKE). The service's core architecture features:

* **多路复用 WebSocket 连接 (Multiplexed WebSockets)**：每个浏览器标签页仅需建立一条独立的 WebSocket 连接，即可在其上多路复用并承载各类数据的实时订阅。
* **精简高效的数据管道 (Streamlined Data Pipelines)**：借助变更数据捕获 (Change-Data-Capture, CDC) 机制，实时将来自 Firestore 和 Spanner 的变更通道数据导入高性能消息总线 NATS。
* **智能增量计算 (Smart Computations)**：订阅服务在内存中动态重算数据视图，利用 `xxh3-128` 算法计算哈希值，且仅在计算结果发生实质性改变时，才向下游推送必要的增量差量数据。
* **响应式鉴权机制 (Reactive Authorization)**：系统将鉴权视为一种独立的响应式数据源，一旦用户权限发生变动，便能立即触发最新的数据视图重算，从而将不必要的无效权限计算大幅削减了约 84%。

> * **Multiplexed WebSockets:** Each browser tab opens a single WebSocket connection, multiplexing various data subscriptions over it.
> * **Streamlined Data Pipelines:** Change-data-capture feeds channel updates from Firestore and Spanner into NATS, a high-performance message bus.
> * **Smart Computations:** Subscriptions recompute views, calculate `xxh3-128` hashes, and transmit only the necessary deltas when outputs change. 
> * **Reactive Authorization:** Authorization is treated as an independent reactive data source, allowing permission modifications to instantly trigger fresh data evaluations—slashing unnecessary permission recomputations by roughly 84%.

## 影子流量保驾护航：实现零故障平滑灰度上线

> ## Shadow Traffic Validated the Rollout

为了确保新老架构平稳过渡，Lovable 率先在影子模式 (Shadow Mode) 下对新服务进行了严格的验证测试：前端浏览器端会并行执行全新的代码执行路径，但在后台默默丢弃返回的负载数据，仍然以旧版 Firestore 的数据源进行页面渲染。这一前瞻性策略帮助工程师团队精准捕获并修复了一系列棘手的边界隐患，例如集群部署引发的客户端重连风暴、错误类型误判以及数据传输包尺寸超限等问题。

> To ensure a seamless transition, Lovable initially tested the service in shadow mode, allowing the frontend to exercise the new code paths while safely discarding payloads and rendering from legacy Firestore sources. This practice helped uncover and resolve edge cases like deployment-induced reconnect storms, misclassified errors, and payload limits. 

借助功能开关 (Feature Flags)，新服务的流量在短短数天内从 1% 稳步提升至 100% 全量覆盖，全程未出现任何性能倒退或用户感知的线上事故。为了妥善应对具有长连接粘性的 WebSocket 连接并消除可能的重连尖峰，Lovable 专门设计了基于连接数的动态负载均衡、精细的自动弹性伸缩指标以及客户端状态指纹校验机制。值得一提的是，整套复杂的核心基础设施从零搭建仅耗费了 40 个实际工作日，这在很大程度上得益于集成测试环境中全自主 AI 编程智能体 (Coding Agents) 的强大助推。

> Using feature flags, availability was gradually ramped up from 1% to 100% of users over several days with zero regressions or user-facing incidents. To handle sticky WebSocket connections and prevent reconnection surges, Lovable implemented connection-based balancing, autoscaling metrics, and client-side state fingerprints. Notably, the core infrastructure took just 40 hands-on working days to build, heavily accelerated by coding agents operating within an integrated testing environment.

## 生产环境收益与未来应用生态扩展

> ## Production Results and Potential App Support

在为期 30 天的生产环境运行监控中，Lovable 记录到的硬核数据充分印证了这套新架构的极致效率：

> During a 30-day measurement period, Lovable’s production metrics highlighted the extreme efficiency of the new architecture:

* **网络负载大幅缩减 (Payload Reduction)**：生产环境累计产生了 26.1 亿次数据补丁帧传输。如果传输传统的全量快照，网络数据总量预估将达到 40 TB；而在数据去重与增量流式传输技术的加持下，实际传输的数据包总体积被骤降至仅 1.11 TB——**负载压缩率高达 97%**。
* **超低端到端延迟 (Latency)**：从底层数据库完成数据写入，到准备好发送给客户端的输出帧，系统测得的处理耗时仅为 66 毫秒 (p50 分位) 和 249 毫秒 (p99 分位)。

> * **Payload Reduction:** Generated 2.61 billion data/patch frames. While full snapshots would have totaled an estimated 40 TB of data, deduplication and delta streaming reduced actual transmitted payloads to just 1.11 TB—a **97% reduction**.
> * **Latency:** The interval between a database write and an outgoing frame being ready registered at 66 milliseconds (p50) and 249 milliseconds (p99).

展望未来，Lovable 正在积极开发领域事件原语 (Domain-Event Primitives)，并探索将这套成熟的实时服务封装为平台内置能力，直接开放给在其平台上构建的各类第三方应用。这一潜在的演进方向将把企业级的后端控制权限与实时数据视图无缝赋能给用户构建的应用程序，从而重塑现代 AI 应用的实时协作体验。

> Looking ahead, Lovable is actively developing domain-event primitives and exploring the possibility of packaging the real-time service as an internal capability for apps built directly on its platform. This potential evolution would bring enterprise-grade, backend-controlled permissions and live data views to customer-created applications.
