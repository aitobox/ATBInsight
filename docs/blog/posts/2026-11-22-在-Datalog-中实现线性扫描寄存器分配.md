# 在 Datalog 中实现线性扫描寄存器分配

> # Linear Scan Register Allocation in Datalog

### 文章背景与核心概要
寄存器分配是现代编译器后端中最核心、也是计算最复杂的优化阶段之一。传统的线性扫描寄存器分配算法本质上是一种强依赖状态变更、高度过程式的贪心算法，通常使用命令式语言实现。本文由作者与程序分析领域著名学者 Yannis Smaragdakis 合作，探索了如何在声明式逻辑编程语言 Datalog 中纯规则化地表达线性扫描算法。文章展示了 Datalog 在处理控制流图重构与活跃性分析时的优雅自如，并揭示了利用“全称量词仿真 (Forall Emulation)”技巧在互递归规则中模拟顺序状态演化与寄存器溢出决策的高级范式。

---

## 摘要

> ## Summary

本文探讨了如何与 Yannis Smaragdakis 合作，在 Datalog 中以纯声明式的方式实现一个完整的线性扫描寄存器分配器 (Linear Scan Register Allocator)。诸如还原控制流图 (Control-Flow Graph, CFG) 以及计算变量活跃区间 (Liveness Intervals) 等分析任务，能够天然映射为 Datalog 的递归推导规则；但要模拟线性扫描中带有强先后顺序的命令式步骤——例如判断生命周期结束释放寄存器、选择溢出受害者 (Spill Victims) 等——则需要借助高级推导技巧。特别是，本实现依赖在有序寄存器集合上的**全称量词仿真 (Forall Emulation)**，从而在相互递归的逻辑规则中精确完成寄存器溢出候选变量的裁决。

> This post explores implementing a complete linear scan register allocator declaratively in Datalog, developed in collaboration with Yannis Smaragdakis. While tasks like recovering control-flow graphs and computing liveness intervals map naturally to recursive Datalog rules, simulating the sequential, imperative steps of linear scan—such as expiring intervals and selecting spill victims—requires advanced techniques. In particular, the implementation relies on **forall emulation** over an ordered set of registers to pick spill candidates within mutually recursive rules.

var_def(0, "R10").
var_def(1, "R11").

var_use(2, "R11").

var_def(3, "R12").
var_def(4, "R13").

var_use(5, "R13").

var_use(8, "R12").

我们还以指令为粒度对控制流进行了建模：明确定义了指令之间的跳转关系，从而在 Datalog 中直接重构出基本块边界与完整的控制流图（此处为篇幅起见略去推导规则）。这就是为什么代码中会出现 `jump(2, 3)`（表示指令 `2` 跳转到指令 `3`）、`ret(16)`（表示指令 `16` 为返回指令）等事实的原因。

## 活跃性分析

> ## Liveness

由于我们对输入数据的建模做了进一步细化（变量不再是在基本块内笼统定义，而是在专有的指令编号处分别定义），因此必须对上一篇文章中的活跃性分析逻辑进行扩充。现在我们在 Datalog 中推导的内容要丰富得多：

> Because we complicated our input data a bit (variables are no longer `def`-ed in blocks, but instead `def`-ed at their own instruction indices), we had to expand our liveness logic from the last post. We now compute a lot more in Datalog:

* 基本块边界（为篇幅起见略去）
* 每条指令归属的具体基本块（为篇幅起见略去）
* 完整的控制流图结构（为篇幅起见略去）
* 每条指令维度的 `live_in`（入口活跃）与 `live_out`（出口活跃）集合（而非针对基本块粒度）
* 变量的生命周期活跃区间

> * Basic block boundaries (omitted for brevity)
> * Which instructions belong to which block (omitted for brevity)
> * The control-flow graph structure (omitted for brevity)
> * `live_in` and `live_out` for each instruction (rather than each block)
> * Liveness intervals

尽管增加了这些内容，活跃性分析仍然是整个实现中最直观、最容易理解的部分。四条相互递归的 Datalog 规则精确定义了 `live_out` 与 `live_in`，完美对应了教科书中的标准数据流分析方程。（其中的传递函数被拆分为了两条显式规则：当某个变量被当前指令使用、或者在该指令出口处活跃且未被该指令定义时，该变量即在入口处活跃。）

> Even with these additions, liveness remains the most straightforward part of the implementation. Four mutually recursive rules define `live_out` and `live_in`, corresponding directly to the standard textbook data-flow equations for liveness. (The transfer function is split into two explicit rules: a variable is live-in if it is used by the instruction, or if it is live-out and not `def`-ed by the instruction.)

```datalog
live_out(insn, var) :-
  block_succ(prev, succ),
  block_head(succ, headinsn),
  live_in(headinsn, var),
  block_tail(prev, insn).

live_in(insn, var) :-
  var_use(insn, var).

live_in(insn, var) :-
  live_out(insn, var),
  !var_def(insn, var).

live_out(insn, var) :-
  live_in(next, var),
  next_in_block(insn, next).
```

这套规则与 Waleed 和我之前构建的活跃性实现非常相似，核心差异仅在于它在细粒度的指令层级而非基本块层级运作。

> This looks quite similar to the liveness implementation Waleed and I built previously, except that it operates at the instruction level rather than the block level.

由于上述规则只输出了逐条指令维度的活跃变量集合，接下来我们需要为每个变量提取出其跨越的完整生命周期区间——即变量处于活跃状态的最早指令与最晚指令。在此处我们可以安全地使用 `min` 和 `max` 聚合算子，因为这套规则*只有在*前面的互递归数据流分析完全达到不动点之后才会执行评估：

> Because those rules only give us per-instruction liveness sets, we next extract the full extent of the interval for every variable—the earliest instruction where it is live and the latest instruction where it is live. We can safely use `min` and `max` aggregations here because this rule is evaluated *only after* the mutually recursive dataflow has reached a fixpoint:

```datalog
// Liveness starts right after start, ends right before end
.decl liveness_interval(start:Instruction, end:Instruction, var:Var)

liveness_interval(start, end, var) :-
  live_out(_, var),
  start = min b : { live_out(b, var) },
  end = max b : { live_in(b, var) }.
```

一旦求出了所有变量的活跃区间，接下来就该为它们分配物理寄存器了。[^intervals]

> Once we have the intervals, we need to assign physical registers to the variables.[^intervals]

## 寄存器分配

> ## Register Assignment

计算中最具挑战性的部分正是线性扫描寄存器分配算法本身。我们借助谓词 `reg_assignment` 对此进行建模，它模拟了在对指令进行线性扫描的每一步推进过程中，算法所处的瞬时分配状态：

> The challenging part of the computation is the linear scan register allocation itself. We encode this using a predicate `reg_assignment`, which simulates the algorithm's state at every step across a linear scan of instructions:

```datalog
// After instruction, this is the register assignment. Var = "none" is a possibility
.decl reg_assignment(insn:Instruction, reg:Register, var:Var)
```

在处理每一条指令时，算法都会跟踪被分配的各个物理寄存器当前存放的内容。当前未存放任何变量的空闲寄存器，会被填入一个对应其寄存器编号的伪变量 (Pseudo-Variable)——例如，当 `0` 号寄存器为空时，它存放的是伪变量 `none_0`。这种编码技巧巧妙地将每一次分配决策都统一转化为了变量之间的优先级对比。在选择需要被溢出的变量时，比较器总是优先选择 `"none"` 伪变量（相当于直接占用空闲寄存器）而非真实变量；而在多个真实变量狭路相逢时，它则执行标准的线性扫描策略：将活跃区间结束时间最晚的那个变量溢出到栈中。

> At every instruction, the algorithm tracks the current contents of each physical register being allocated. Registers not currently holding a variable instead hold a pseudo-variable corresponding to the register's name—for instance, when register `0` is empty, it contains the variable `none_0`. This encoding lets us phrase every allocation decision as a comparison between variables. When choosing a variable to spill, the comparator always prefers a `"none"` variable over a real one; between real variables, it applies the standard linear scan policy of spilling whichever variable's liveness interval ends last.

### 处理扫描过程中的每一步骤

> ### Handling Each Step in the Scan

代码中的注释详细阐明了算法需要处理的各种情况：

> Comments in the code explain all the cases the algorithm handles:

* **状态顺延 (Propagation)：** 如果在当前指令处既没有活跃区间到期失效，也没有新变量被定义 (`def`/赋值)，则现有寄存器与变量的映射关系原封不动顺延至下一条指令。
* **生命周期终止 (Expiration)：** 当某个变量的活跃区间结束时，存放该变量的寄存器（若有）会被重置为其对应的 `"none"` 伪变量。
* **分配与溢出 (Allocation and Spilling)：** 最核心的情况发生在遇到新变量的 `def` 指令时。我们必须做出溢出决策——即判定应该由哪个寄存器（如果有的话）来容纳这个新定义的变量。受害者选择策略被高度模块化地封装在 `better_victim_var` 谓词中，该谓词预先算好了所有可能变量对之间的比较优劣结果。

> * **Propagation:** The register-to-variable assignment is carried forward unchanged if no liveness interval ends and no new variable is `def`-ed (assigned) at the current instruction.
> * **Expiration:** When a liveness interval expires, the register holding that variable (if any) is reset to its corresponding `"none"` pseudo-variable.
> * **Allocation and Spilling:** The interesting case occurs when we encounter a new variable `def`. We must decide which variable to spill—that is, which register (if any) should hold the newly `def`-ed variable. The victim-selection policy is completely modular and encapsulated in a `better_victim_var` predicate, which pre-calculates the result of all possible variable comparisons.

### 全称量词仿真

> ### Forall Emulation

这里的核心绝技正是编码在 `best_victim_up_to_reg` 与 `all_reg_best_victim` 两组规则中的**全称量词仿真 (Forall Emulation)** 机制（后者虽然可以微不足道地内联简化，但为了让这种设计模式更加清晰直观，我们特意将其保持独立）。全称量词仿真按顺序依序遍历所有寄存器，并在每一步维护并传递当前找到的最佳受害者变量。当我们遍历到最后一个寄存器时，便得出了全局最优的溢出候选受害者。

> The core trick here is the **forall emulation** encoded in the rules for `best_victim_up_to_reg` and `all_reg_best_victim` (the latter could trivially be inlined, but is kept separate to make the pattern explicit). The forall emulation iterates over all registers in order, tracking the current best victim variable at each step. Once we reach the final register, we have the overall best victim.

回到核心算法的主流程：

> Returning to the core algorithm:

* 如果选出的最佳溢出受害者就是刚刚被定义的变量自身，那么所有现有的寄存器分配保持不变，新定义的变量不会被分配寄存器（直接溢出到内存）。
* 如果最佳受害者是当前正驻留在某个物理寄存器中的变量，那么该寄存器会被重新分配给新定义的变量，而其余所有寄存器存放的内容则继续原样复制传递到下一条指令。

> * If the chosen victim variable is the `def`-ed variable itself, all existing register assignments are carried over unchanged, and the `def`-ed variable does not receive a register.
> * If the best victim is a variable currently held in a register, that register is reassigned to the `def`-ed variable, while all other registers are copied over to the next instruction.

全称量词仿真属于 Datalog 中相当精深的高级编程技巧。通常情况下，全称量词 (`forall`) 可以通过否定与存在量词组合 (`not exists`) 来优雅改写；但当涉及的谓词参与了相互递归 (Mutual Recursion) 时，这种改写方法便不再奏效，必须依赖全称量词仿真。从计算复杂性理论的视角来看，全称量词仿真对于 Datalog 具备表达所有多项式时间 (**PTIME**) 算法的能力至关重要（尽管在工程实践中，现代 Datalog 引擎通常引入了算术运算与元组支持，使其具备了图灵完备性）。如果脱离了全称量词仿真——这种技术本质上依赖底层对数据值的严格排序——未经扩展的纯 Datalog 只能表达多项式时间算法的一个真子集。

> Forall emulation is an advanced Datalog coding pattern. It is required whenever a universal quantifier (`forall`) cannot simply be rewritten using negation (`not exists`) because the predicates involved participate in mutual recursion. From a complexity theory standpoint, forall emulation is essential for Datalog to express all **PTIME** algorithms (though practical Datalog engines also include arithmetic and tuples, making them Turing-complete). Without forall emulation—which itself relies on an underlying ordering of values—pure Datalog without extra features can only express a strict subset of polynomial-time algorithms.

### 简化假设与未来优化方向

> ### Simplifications and Future Optimizations

该算法在最后一步的处理上做了一定的简化：只有当某个物理寄存器能够容纳变量的整个生命周期时，才会将该寄存器分配给该变量。这是线性扫描最精简的原型形态；开发者完全可以对其进行拓展，允许物理寄存器仅在变量生命周期的一部分时间段内为其服务。

> The final step of the algorithm assigns a register to a variable only if that register can hold the variable for its entire lifetime. This is the simplest form of linear scan; one could extend it to allow registers to hold a variable for only part of its lifetime.

此外，在提升推导效率方面，当前的实现还有几处值得探索的优化空间：

> There are also several ways to improve the implementation's efficiency:

1. **跳过无实质动作的指令：** 目前的扫描过程会逐一走过每一条指令。实际上，算法完全可以直接从一个“关键事件指令”跳转到下一个关键指令——即只在出现变量定义 (`def`) 或区间到期时触发更新，从而跳过那些纯粹进行寄存器映射复制的中间指令。
2. **按需惰性对比：** 与其在一开始就预先计算出所有可能变量对在 `better_victim_var` 中的胜负关系，不如采用请求-响应 (Request-Response) 模式进行惰性求值，仅针对实际执行过程中真正狭路相逢、需要做出取舍的变量对触发比较推导。

> 1. **Skip uninteresting instructions:** Currently, the scan iterates over every single instruction. Instead, it could jump directly from one "interesting" instruction to the next—namely, `def`s and interval expirations—skipping instructions that merely copy register assignments forward.
> 2. **On-demand comparisons:** Rather than precomputing `better_victim_var` for all possible variable pairs up front, victim comparisons could be evaluated lazily using a request-response pattern, firing only for the pairs of variables that actually need to be compared during execution.
