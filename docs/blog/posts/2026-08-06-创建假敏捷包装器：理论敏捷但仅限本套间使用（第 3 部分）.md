# 创建假敏捷包装器：理论敏捷但仅限本套间使用（第 3 部分）

### 文章背景与核心概要
在 C++/WinRT 与 COM 编程中，跨套间（Apartment）访问不可封送（Non-marshalable）对象一直是一个挑战。本文是创建“假敏捷（Fake Agile）”引用系列的第三部分，着重解决了标记有 `INoMarshal` 的接口对象无法直接放入全局接口表（Global Interface Table, GIT）的问题。作者通过引入一个可封送的包装结构体 `force_marshal` 来封装非封送指针，使得该对象在表面（理论）上具备敏捷性。当在错误的套间中使用该对象时，程序会安全抛出定义明确的异常，从而避免引发严重的未定义行为（Undefined Behavior）。

---

## 克服 `INoMarshal` 障碍

> ## Overcoming the `INoMarshal` Obstacle

此前，我们尝试使用全局接口表（GIT）来持有另一个套间中对象的引用，并设计使其在该套间关闭时自动失效。然而，该方案陷入了困境，因为被标记为 `INoMarshal` 的对象是无法存入 GIT 中的。

> Previously, we attempted to use the Global Interface Table (GIT) to hold a reference to an object in another apartment, designed to automatically expire when that apartment wound down. However, that plan broke down because objects marked `INoMarshal` cannot be stored in the GIT.

为了解决这个问题，我们采取了“强硬手段”：将不可封送的对象置于一个*可封送*的对象内部。

> To solve this, we force the square peg into the round hole: we place the non-marshalable object inside an object that *is* marshalable.

```cpp
template<typename Smart>
struct force_marshal :
    winrt::implements<force_marshal<Smart>, ::IUnknown, winrt::non_agile>
{
    force_marshal(Smart const& p) : m_p(p) {}
    Smart m_p;
};
```

`force_marshal<Smart>` 对象负责托管指向 COM 对象的不可封送智能指针，并在其外层暴露一个可封送的包装器。由于被封装的对象本身不是敏捷的（agile），因此该包装器也不能是敏捷的。*（如果包装器是敏捷的，我们就会又绕回最初的问题：如何确保 `m_p` 在正确的套间中被析构？）*¹

> The `force_marshal<Smart>` object babysits a non-marshalable smart pointer to a COM object and exposes a marshalable wrapper around it. Because the wrapped object is not agile, the wrapper cannot be either. *(If the wrapper were agile, we would loop right back to our original problem: How do we ensure that `m_p` is destructed in the correct apartment?)*¹

---

## 整合所有逻辑

> ## Putting It All Together

定义好包装器之后，我们就可以将不可封送的对象放入包装器中，再将包装器存入全局接口表（GIT）中：

> With our wrapper defined, we can place the unmarshalable object inside the wrapper, and then place the wrapper into the Global Interface Table:

```cpp
template<typename T>
struct fake_agile_ref
{
    ⟦ ... ⟧

    fake_agile_ref(Smart const& p) : m_raw(winrt::get_abi(p))
    {
        if (m_raw) {
            m_context = winrt::capture<IContextCallback>(CoGetObjectContext);
            m_token = get_context_token();
            m_git = winrt::create_instance<IGlobalInterfaceTable>(CLSID_StdGlobalInterfaceTable);
            winrt::check_hresult(m_git->RegisterInterfaceInGlobal(
                winrt::make<force_marshal<Smart>>(p).get(),
                __uuidof(IUnknown), &m_cookie));
        }
    }

    ⟦ ... ⟧
};

template<typename T> fake_agile_ref(winrt::com_ptr<T> const&)
    -> fake_agile_ref<T>;
template<typename T> fake_agile_ref(T const&)
    -> fake_agile_ref<T>;
```

### 最终效果

> ### The Result

我们成功为不可封送的对象创建了一个敏捷包装器。该包装器在**理论上**（你可以将其传递给任何线程）是敏捷的，但在**实践中**并非如此：试图从错误的套间中调用它会抛出异常。

> We have successfully created an agile wrapper around an unmarshalable object. This wrapper is agile **on paper** (you can pass it around to any thread), but not **in practice**: attempting to use it from the wrong apartment throws an exception.

关键在于，这种行为是*明确定义的（well-defined）*，与直接在错误套间中使用不可封送对象所导致的*未定义行为（undefined behavior）*形成了鲜明对比。

> Crucially, this behavior is *well-defined*, contrasting sharply with the *undefined behavior* that occurs when you directly use an unmarshalable object from the wrong apartment.

## 补充讨论：VPN 类比

> ## Bonus Chatter: The VPN Analogy

现在我们拥有了一个可封送的包装器，理论上我们*能够*利用该包装器跨套间调用原始的非封送对象：

> Now that we have a marshalable wrapper, we *could* theoretically use that wrapper to call the original non-marshalable object across apartments:

| Original Apartment | | | Other Apartment |
| :--- | :---: | :---: | :--- |
| **Wrapper** | $\leftarrow$ | $\leftarrow$ | **Caller** |
| $\downarrow$ | | | |
| **Non-marshalable** | | | |

虽然非封送对象会阻止来自其他套间的直接调用，但由于包装器与非封送对象处于*同一个*套间内，因此包装器的内部调用实际上发源于正确的套间内部。

> The non-marshalable object blocks incoming calls directly from other apartments, but because the wrapper lives in the *same* apartment as the non-marshalable object, its internal calls originate from within the correct apartment.

你可以将该包装器想象为通往原始套间的 **VPN**——它允许外部调用以“隧道”方式穿透进来，同时向非封送对象伪造调用发源于本地套间的假象。

> You can think of the wrapper as a **VPN** into the original apartment—allowing calls to tunnel in from the outside while making it appear to the non-marshalable object that they originated locally.

尽管我们*可以*这么做，但我们选择不这么做。原始对象将其自身声明为不可封送是有其深层原因的；我们应当尊重其设计选择，而不是耍小聪明去绕过它的安全边界。

> While you *could* do this, we choose not to. The original object declared itself non-marshalable for a deliberate reason; we respect that design choice rather than playing clever tricks to bypass its security boundaries.

---

*¹ 有两位评论者掉入了陷阱，建议我们将非封送对象封装在一个实现了 `IMarshal` 的对象中。实现 `IMarshal` 本质上是在宣称：“我已经足够复杂，能够自行处理自定义封送（如敏捷性）。”然而，我们恰恰*希望*自己是一个普通、非敏捷的对象，以便让 COM 为我们处理标准封送。*

> *¹ Two commenters fell into the trap of suggesting we wrap the non-marshalable object inside an object implementing `IMarshal`. Implementing `IMarshal` essentially claims: "I am sophisticated enough to handle custom marshaling (like agility)." However, we *want* to be a boring, non-agile object so that COM handles standard marshaling for us.*
