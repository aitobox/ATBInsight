从字节码到静态单赋值：构建虚拟栈的抽象解释器实战

文章背景与核心概要

将基于栈的字节码转换为现代编译器不可或缺的静态单赋值 (Static Single Assignment, SSA) 形式，常被视为即时编译器 (Just-In-Time, JIT) 底层极其复杂的黑魔法。然而在工程本质上，这一转换的核心原理出人意料地纯粹而优雅。本文以通俗易懂的视角与 Ruby 代码实战，深入浅出地讲解了如何利用“虚拟操作数栈”构建一个微型抽象解释器 (Abstract Interpreter)——它在编译期跟踪数据值的来源而非具体运行状态，从而举重若轻地把线性的字节码序列无缝升华为清晰的 SSA 中间表示 (IR)。这一经典技巧不仅驱动着 Java HotSpot 等工业级虚拟机的高效编译，更为理解现代编译器中间层架构提供了绝佳的认知切入点。

概述

Summary

将基于栈的字节码转换为静态单赋值 (Static Single Assignment, SSA) 形式，是现代即时编译器 (Just-In-Time, JIT) 架构中的关键基石。在工业级编译器的真实实现中，为了应对各种复杂的操作码 (Opcode) 与边界极端情况，代码往往动辄多达数千行；然而，其底层的核心机制却出人意料地简单纯粹。只要借助一个跟踪“数据来源”而非“具体运行状态”的抽象解释器 (Abstract Interpreter)，开发者就能举重若轻地把线性的字节码序列优雅转换为直观的 SSA 中间表示。

Converting stack-based bytecode into Static Single Assignment (SSA) form is a fundamental step for modern Just-In-Time (JIT) compilers. While real-world implementations can span thousands of lines to handle complex opcodes and edge cases, the core mechanism is surprisingly simple. By leveraging an abstract interpreter that tracks the origin of values rather than their concrete execution states, developers can gracefully transform sequential bytecode instructions into direct SSA representations.

倘若栈是虚拟的会怎样？

What If a Stack, But Virtual?

基于栈的字节码在设计上都有一个基本假定：在运行时，所有操作都在一个操作数栈上进行。这也意味着，每一条操作码都会隐式地从栈中弹出输入数据，并隐式地将计算结果压入栈中作为输出。

The bytecode assumes that when it is run, it will be operating on a stack. This means that every opcode has implicit stack inputs and implicit stack outputs.

举例来说，指令 push 3 不需要从栈中获取任何输入（栈输入为空），但会产生一个栈输出（将数值 3 压栈）。相比之下，加法指令 add 则需要消耗两个栈输入，并生成一个栈输出。当然，也有一些像 nop (空操作) 这样的指令，既不需要输入也不产生任何输出。据我所知，在绝大多数规范中，所有字节码指令至多只产生一个栈输出。

push 3, for example, has empty stack inputs and one stack output. By contrast, add has two stack inputs and one stack output. Some instructions such as nop are empty on both counts. As far as I can tell, all instructions have at most one output.

只要审视字节码本身，这些输入和输出的数量其实是一目了然的：我们完全可以在编译阶段对每个操作码所需的入栈和出栈数量进行静态推导。虽然也有少部分指令支持可变参数——比如方法调用指令 send (call)——但它们都会在相邻的操作数或指令字段中明确携带具体的参数个数。

These counts are known when looking at the bytecode: we can reason statically about how many inputs and outputs each opcode has. Some are variadic, such as send (call), but they come bearing an argument count in a nearby field.

现在，让我们通过直观展示每条指令执行后的栈状态，来模拟上述示例在虚拟机 (VM) 中的具体运行过程。为了便于观察，我们将操作数栈从左到右显示为一个列表，其中最左侧代表栈底，最右侧代表栈顶。

Let’s model how the first example runs on the VM by adding a view of the stack after each instruction has run. The stack will be displayed as a list left-to-right, where the left is the bottom and the right is the top.

       ; []
push 3 ; [3]
push 4 ; [3, 4]
add    ; [7]

正因为每条指令的输入和输出数量在静态分析时是完全固定的，所以当即时编译器（如 Ruby 内部的 ZJIT）自上而下读取字节码时，我们根本不需要等到运行时，完全可以在编译期模拟执行所有的入栈与出栈操作。

Because the input counts and output counts are static, when ZJIT reads through the bytecode, we can run the stack parts of it at compile-time.

在编译期间，我们其实并不真正关心栈中具体的数值究竟是多少，唯一需要追踪的是这些数值“究竟来自哪里”。所谓“来自哪里”，意思就是我们为每一条生成结果的指令赋予一个唯一的名字，并直接用这个名字来代指该指令的输出结果。经典论文《Java 6 中 Java HotSpot™ 客户端编译器的设计》 (PDF) 中的一段精辟总结对此做了极佳的诠释：

We don’t really need to know what the values on the stack are; we only need to keep track of where they came from. And when I say “where they came from”, I mean that we name each instruction and refer to its output by the instruction’s name. I like how the paper Design of the Java HotSpot™ Client Compiler for Java 6 (PDF) puts it:

💬 [原文引用 / Original Quote]: “一条用于加载或计算数值的指令，既代表该运算本身，也同时代表其计算结果；因此，所有操作数都可以直接表示为指向先前指令的指针。”
"An instruction that loads or computes a value represents both the operation and its result, so that operands can be represented as pointers to previous instructions."

将这个思想套用到前面的例子中，其演进过程就会变成下面这样。除了虚拟的栈状态之外，我还额外列出了逐步生成的 SSA 指令，以直观展现我们正在构建的新代码：

Here is what that looks like for the above example. In addition to the run-time stack, I will also write the SSA instruction to indicate that we are generating new code:

       ; []
push 3 ; v0 = const 3
       ; [v0]
push 4 ; v1 = const 4
       ; [v0, v1]
add    ; v2 = add v0, v1
       ; [v2]

这个效果堪称精妙！我们不知不觉中已经把基于栈的隐式字节码，转换成了一种指令可以直接按名字引用其输入操作数的形式。不过细心的读者可能会发现，v0 和 v2 最终都停留在了同一个栈槽位中（即栈底的第一个元素）。这也就是为什么我之前会带着保留说，这只是“差不多给每个栈槽位赋予了一个 SSA 变量值”。

This is neat! We have transformed stack based bytecode to a form where instructions can directly reference their inputs. You may notice, though, that v0 and v2 both end up in the same stack slot (the first element). This is why I said earlier “giving an SSA value to each stack slot, ish”.

这两者之间的本质区别在于时间。v0 曾在某个时间点占据了操作数栈的位置，而此时此刻占据该位置的变成了 v2。这也是我常常把 SSA 形象地描述为“将时间维度推进穿透到中间表示 (IR) 之中”的原因。

The difference between the two is time. v0 was in the operand stack at one point but now v2 is. This is kind of why I describe SSA as “pushing time through the IR”.

理论梳理清晰了，接下来让我们动手写代码实现它！

Alright, let’s implement it.

代码实现

Implementation

我们首先构建一个真正的 (具体) 字节码解释器，它在运行时直接操作一个存储具体数值的值栈 (Value Stack)。这段实现可以让你清晰窥见 Ruby 虚拟机底层的极简工作模型：

We’ll start with the real (“concrete”) interpreter of the bytecode, which operates on a value stack. This gives you a simplified version of how Ruby internals work:

def interpret(bytecode)
  stack = []
  bytecode.each do |op|
    case op
    in [:push, c]
      stack << c
    in [:add]
      right = stack.pop
      left = stack.pop
      stack << left + right
    else
      raise "Unknown op #{op}"
    end
  end
  stack.pop
end

bytecode = [
  [:push, 3],
  [:push, 4],
  [:add],
]

puts interpret(bytecode)  # 7

现在，让我们来看看与之对应的抽象解释器。两者最大的不同在于，抽象解释器操作的是一个用于记录变量名的 SSA 栈。你会发现，两者的代码结构几乎如出一辙：

Now let’s look at the abstract interpreter, which by contrast operates on an SSA stack. You can see that they are quite similar looking:

def to_ssa(bytecode)
  code = []
  stack = []
  bytecode.each do |op|
    case op
    in [:push, c]
      name = :"v#{code.length}"
      code << "#{name} = const #{c}"
      stack << name
    in [:add]
      name = :"v#{code.length}"
      right = stack.pop
      left = stack.pop
      code << "#{name} = add #{left}, #{right}"
      stack << name
    else
      raise "Unknown op #{op}"
    end
  end
  code
end

bytecode = [
  [:push, 3],
  [:push, 4],
  [:add],
]

puts to_ssa(bytecode)
# v0 = const 3
# v1 = const 4
# v2 = add v0, v1

变量名 name 叫什么其实无所谓，只要全局唯一即可。为了简明易读，我直接选用了单调递增的 code 数组长度作为编号。这其实就是前面提到的 HotSpot 论文中“真实内存指针方案”在数组/向量数据结构中的优雅映射。

The names could be anything as long as they are unique. For simplicity and ease of reading, I picked the length of the code array, which grows monotonically. This is an array/vector-based analogue to the real-pointer approach in the HotSpot paper from above.

大功告成！你看，你已经亲手打造出了一个精巧的抽象解释器。

Ta da! You have built a small abstract interpreter.

如果想要将这一机制推广到全局（即处理条件分支、循环等复杂控制流），你还需要引入某种跨基本块 (Basic Block) 的数据流传递机制，例如 Φ节点 (Phi Node) 或者是基本块参数 (Basic Block Parameters)。我可能会在未来的博文中更深入地探讨这个话题；不过眼下，你可以先阅读我整理的关于该主题的他山之石精选合集。

Now to make it global (to handle control flow) you need some kind of inter-basic-block data flow mechanism such as phi nodes or basic block parameters. Perhaps more on that in another post, but for now, you may enjoy my collection of other people’s writing about that.

总结与思考

Conclusion

我最初曾想把这篇博文命名为《其实你也能发明抽象解释》之类的调调，但我很快打消了这个念头——因为我总觉得这类标题带有某种傲慢，潜意识里假设读者不够聪明或者自认为不够聪明。也许更恰当的说法是：我们本就可以共同构想出它。

I originally wanted to title this blog post “you could have invented abstract interpretation” or similar, but I decided that I find those titles obnoxious because they assume the reader is or thinks of themself as unintelligent. Perhaps we could have invented it.

本文现在的标题（从字节码到 SSA：一颗指令式珍珠），带着一点幽默诙谐的味道，致敬了那些常被冠以“函数式珍珠 (Functional Pearl)”之名、本该简洁明快却往往让人云里雾里的学术论文；同时，它也是对 Andrew Appel 的经典名作《SSA 即函数式编程》 (PDF) 的一份温和致意。

The title is a bit of a tongue-in-cheek nod to the “functional pearl” papers that I always felt should be simpler than they are but leave me confused. And also kind of a nicer nod to SSA is Functional Programming (PDF) by Andrew Appel.
