文件系统发生写入错误后的未知状态与架构权衡

文章背景与核心概要

在计算机系统中，当应用程序向磁盘写入数据失败时，我们往往直觉地认为操作“完全没发生”或“直接报错回滚”。然而在现代复杂的存储设备与硬件控制器面前，一旦写入发生 I/O 错误，底层的物理介质究竟写入了多少、处于何种状态实际上是完全不可知的。这种硬件物理层面的不确定性，直接给操作系统内核与现代文件系统 (如 OpenZFS) 带来了严峻的一致性困境：内存中的数据对象究竟该保留还是删除？为了兼顾数据完整性与系统高可用，文件系统在传统的“遇错直接停机 (Panic)”与“容忍错误继续运行 (Continue)”之间做出了艰难的架构权衡。

概要

Summary

当文件系统遭遇写入输入输出 (I/O) 错误时——例如在创建目录的过程中——底层存储介质真实的物理与逻辑状态便会陷入未知的混沌之中。存储设备往往无法准确汇报某次写入操作究竟是已经成功落盘、部分写入完成，还是在触碰介质前就彻底失败。当数据持久化 (Persistence) 受阻时，这给像 ZFS 这样的现代文件系统带来了棘手的两难抉择：既要防范磁盘上潜在的数据损坏风险，又要维系操作系统内存中状态的一致性。

When a filesystem encounters a write I/O error—such as during the creation of a directory—the true physical and logical state of the storage becomes uncertain. Devices cannot reliably report whether a write succeeded, partially succeeded, or failed entirely before encountering an error. This creates a difficult dilemma for filesystems like ZFS regarding how to handle both on-disk corruption risks and in-memory consistency when persistence fails.

问题的根源：ZFS 与写入错误

The Root of the Problem: ZFS and Write Errors

在围绕 mkdir 命令及其底层系统调用 mkdir(2) 抛出错误时的行为讨论中，关于文件系统韧性经常会出现这样一个疑问：

In discussions regarding mkdir's behavior when mkdir(2) experiences an error, a common question arises regarding filesystem resilience:

💬 [原文引用 / Original Quote]: “这难道不纯粹是 ZFS 自身的问题吗？如果在创建目录时遇到了任何差错，它究竟为什么还会允许这个目录继续存在呢？”

“Isn't the problem here squarely with ZFS? What in the world is it doing letting the directory live if there was any problem at all birthing it?”

ZFS 的这一具体案例 ( 在官方测试用例中也有体现 ) 发生在 ZFS 向磁盘发起写入以确保新目录持久化存储时，磁盘却返回了一个 I/O 错误。

The specific ZFS situation (also tested here) occurs when ZFS sends a write to the disk to make a directory creation durable, only to receive an I/O error in return.

然而，对于任何文件系统而言，普遍面临的核心难题在于：一旦发生写入 I/O 错误，现实世界的真实物理状态就会变得未知且不可捉摸。这不仅适用于一般的常规写入，在涉及对象创建等元数据 (Metadata) 操作时更是尤为突出。

However, the general problem for any filesystem is that after a write I/O error, the true state of the world is unknown and uncertain. This applies to writes in general, but it is especially pronounced during metadata operations like object creation.

为什么写入错误会带来不确定性？

Why Write Errors Create Uncertainty

硬件设备返回的写入 I/O 错误或 I/O 超时，仅仅代表“某个环节出了故障”。它并不能说明数据到底有没有真正触及并写入物理存储介质：

A device write I/O error or I/O timeout only communicates that a problem occurred. It does not indicate whether the write actually made it to the storage media:

  • 时序模糊性 (Timing ambiguities)：除非硬件设备在错误代码中给出明确承诺，否则文件系统根本无从知晓错误是在写入完成之前、期间还是之后发生的。
  • 部分写入 (Partial writes)：当一次写入涉及多个磁盘扇区时，可能只有一部分扇区成功提交到了介质中，而另一部分却写入失败。
  • 数据损坏 (Data corruption)：存储驱动器在发生写入错误后通常不对介质上的残留数据做任何保证。最终留下的数据可能既不是旧版本，也不是新版本，而是一份半新半旧的混合残片，甚至是纯粹的损坏乱码 (Garbage)。
  • Timing ambiguities: Unless the device explicitly promises otherwise in its error code, the filesystem cannot know if the error occurred before, during, or after the write completed.
  • Partial writes: When writing multiple sectors, some sectors may successfully commit to media while others do not.
  • Data corruption: Storage drives generally make no guarantees about the data remaining after a write error. The resulting data may be neither the old version nor the new version, but rather a hybrid or pure corruption (garbage).

(虽然事后立即尝试将数据重新读取一遍有时能够帮助理清状态，但这种尝试在实践中往往同样会失败，甚至可能让硬件故障雪上加霜)。

(While immediately attempting to read the data back can sometimes clarify the state, it frequently fails or exacerbates the problem).

内存状态与磁盘状态的割裂

In-Memory State vs. Disk State

除了物理存储介质带来的不确定性之外，文件系统或操作系统内核 (Kernel) 可能已经在系统内存中建立了全新状态的数据结构表示。

Beyond the physical uncertainties of the storage media, the filesystem or kernel may have already established in-memory representations of the new state.

对于新建的文件系统对象，通常的做法是先在内存中构建好该对象，最后一步才将其持久化刷新到磁盘介质上。而一旦这一步持久化发生故障，文件系统便面临着艰难的二选一抉择：

For new filesystem objects, the in-memory version is typically created first, with persistence to disk handled as the final step. When this persistence fails, the filesystem faces a difficult choice:

  1. 清理并移除内存中的对象：应用程序可能会观察到某个对象在没有任何显式删除操作的情况下突然凭空消失；或者恰恰相反，如果磁盘底层其实已经成功完成了写入，该对象后续又会“神奇地”重新冒出来。
  2. 保留内存中的对象：这就会导致类似 ZFS 展现出的行为现象——即使 mkdir(2) 系统调用明确返回了错误，该目录在内存中却依然可见；然而，如果它在磁盘上从未真正物理生成过，它随后便可能在卸载或重载时离奇消失，或者在后续访问中引发新的故障。
  1. Remove the in-memory object: Programs might observe an object that appears and disappears without explicit user action, or conversely, it may "magically" reappear later if the disk turns out to have successfully written it after all.
  2. Keep the in-memory object: This leads to scenarios like ZFS's behavior, where a directory appears to exist despite the mkdir(2) system call returning an error—though it may subsequently vanish or trigger future faults if it never truly materialized on disk.

乱局之下的抉择：停机恐慌还是继续运行？

Handling the Mess: Panic vs. Continue

应对这种状态歧义的传统策略之一，便是在发生未处理的写入错误时立即冻结文件系统或触发系统崩溃恐慌 (Panic)，将文件系统转为只读或挂起状态，交由系统管理员事后人工介入排查损坏。

One traditional way to deal with this ambiguity is to immediately freeze or panic the filesystem the moment an unhandled write error occurs, leaving a system administrator to sort out the corruption by hand.

ZFS 默认采用这种极其保守的防御性策略，而这有时会让运维人员与用户感到十分棘手与沮丧。因此，ZFS 也提供了绕过冻结、仅向调用方直接返回 I/O 错误的配置选项 (例如 failmode=continue 设置)。然而，一旦文件系统选择在持续出现写入错误的情况下硬着头皮继续运行，它就必须无可避免地接受并承受这些与生俱来的状态不确定性。

ZFS adopts this defensive approach by default, which can frustrate users. Consequently, ZFS provides an option to bypass freezing and simply return I/O errors instead (such as the failmode=continue setting). Yet, once a filesystem chooses to continue operating in the face of active write errors, it must inevitably live with these inherent uncertainties.
