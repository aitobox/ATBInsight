告别侵入式验证码：利用轻量级工作量证明 (PoW) 防御 Web 表单垃圾机器人

Protect Your Web Forms Against Spam Bots

文章背景与核心概要

在 Web 开发中，公开表单（如博客评论区、留言板或注册表单）历来是自动化垃圾机器人狂轰滥炸的重灾区。为了抵御垃圾骚扰，传统方案往往依赖各种侵入式的第三方验证码 (CAPTCHA) 服务，但这不仅严重割裂了正常用户的交互体验，还带来了额外的隐私追踪与外部依赖风险。本文介绍了一种优雅、轻量且无需外部服务的自建防御方案——巧妙借鉴加密货币与早期反垃圾邮件中的工作量证明 (Proof-of-Work, PoW) 思想，将防御重心从服务器端转移至客户端浏览器。在用户点击提交的极短瞬间（1 到 2 秒），浏览器利用原生 Web Crypto API 快速求解一道由后端动态下发的哈希谜题，而自动化刷单脚本则因无法或不愿承受高昂算力成本而被拒之门外。基于 Python、Flask 与 WTForms 的完整实战落地方案，成功帮助开发者将每天数十条垃圾信息直接降至近乎为零，实现极佳的用户体验与出色的防刷效果双赢。

核心概要

Summary

在本文中，作者分享了一套量身定制且对用户极度友好的解决方案，无需依赖任何侵入式的第三方验证码 (CAPTCHA) 服务，就能彻底击溃 Web 表单上无休止的垃圾机器人攻击。该技术巧妙借鉴了常见于加密货币与反垃圾邮件协议中的“工作量证明 (Proof-of-Work, PoW)”理念，将计算负担转移给客户端浏览器，仅在表单提交时引入一段用户几乎感知不到的微小计算延迟（1 到 2 秒）。整套方案借助 Python、Flask、WTForms 和 JavaScript 实现，成功将博客评论区原本每天数十条的垃圾轰炸直接压缩至近乎为零。

In this article, the author shares a custom, user-friendly solution to combat relentless spam bot attacks on web forms without relying on intrusive third-party services like CAPTCHAs. Inspired by the "proof-of-work" concept (commonly used in cryptocurrency and anti-spam protocols), the technique shifts the burden to the client's browser, requiring a negligible computation delay (1–2 seconds) upon form submission. Implemented using Python, Flask, WTForms, and JavaScript, this approach successfully reduced blog comment spam from dozens of daily messages to nearly zero.

1. 工作量证明方案简介

1. Introduction to Proof-of-Work Solutions

工作量证明机制最早在 20 世纪 90 年代被提出，初衷正是为了对抗垃圾邮件。虽然它后来因被 Bitcoin 引入挖矿而声名远扬，但如今这项经典技术已经在现代安全项目中强势回归，例如 Cloudflare Turnstile 等防机器人服务便深度融合了该理念。

Proof-of-work schemes were originally devised in the 1990s to fight email spam. While infamously co-opted by Bitcoin for mining, they have made a strong comeback for deterring bots in modern projects like Cloudflare Turnstile.

与传统的验证码不同，工作量证明挑战完全在后台由代码静默完成，根本不需要用户辨认红绿灯或旋转图片：

Unlike CAPTCHAs, proof-of-work challenges are solved entirely through code behind the scenes:

  • 服务端下发一道程序化挑战谜题；
  • 客户端浏览器在极短的时间内（零点几秒至一两秒）自动完成求解；
  • 服务端以极低的计算开销快速核验求解结果的有效性。
  • The server issues a programmatic challenge.
  • The client's browser solves it in a fraction of a second.
  • The server verifies the solution with minimal computational effort.

对于普通的 Web 表单而言，我们只需要在前端挂载一个轻量级 JavaScript 求解器，拦截表单的 submit 提交事件，并将算出的答案作为一个隐藏字段追加到表单中。这直接给恶意发帖者来了个猝不及防的沉重打击——因为绝大多数自动化发帖脚本根本不会运行完整且开启 JavaScript 的真实浏览器环境，更别提为每一次批量请求浪费宝贵的 CPU 算力去硬解密码学谜题了。

For web forms, a JavaScript solver hooks into the form's submit event, appending the solution as a hidden field. This throws a curveball at spammers, as most automated scripts do not use real browsers with JavaScript enabled—let alone want to waste CPU cycles solving cryptographic puzzles.

2. 深入理解工作量证明的运作原理

2. Understanding How Proof-of-Work Works

这项任务的核心思想十分简单直接：寻找一个特定字符串，使得它在经过类似 SHA-512 这类密码学哈希函数计算后，输出的哈希值满足某些严苛特征（例如以预先设定数量的十六进制零开头）。

The typical task involves finding a string that, when hashed with a cryptographic function like SHA-512, yields a hash with specific properties (such as starting with a predetermined number of hexadecimal zeros).

举个例子，我们来看一道 难度 1 (Level 1) 的挑战：寻找一个以 "abcde" 为前缀的字符串，使其 SHA-512 哈希值以单个字符 0（即 4 个全零比特位）开头。

For example, consider a Level 1 challenge: find a string starting with prefix "abcde" that produces a SHA-512 hash beginning with a single 0 (four zero bits).

在这个实验中，计算机尝试了 12 次才算出了一个以 0 开头的哈希值。因此，数字 12 就是一个有效的求解答案。如果进一步增加前导零的要求数量（例如难度 2、难度 3 等），计算难度将呈现指数级飙升，从而让试图并发批量发帖的垃圾机器人寸步难行。

Here, 12 attempts were required to find a hash starting with 0. Thus, 12 is a valid solution. By increasing the required leading zeros (Level 2, Level 3, etc.), the computational difficulty increases exponentially, deterring automated spam bots.

3. 客户端 JavaScript 求解实现

3. JavaScript Implementation

为了在用户提交表单时让浏览器在后台静默完成运算，我们可以直接使用所有现代浏览器均原生内置的 SubtleCrypto API：

To execute this process in the browser during form submission, we use the native SubtleCrypto API available in all modern browsers:

async function sha512(message) {
  const encoder = new TextEncoder();
  const data = encoder.encode(message);
  const hash = await window.crypto.subtle.digest("SHA-512", data);
  return new Uint8Array(hash).toHex();
}

async function solve(challenge, level) {
  let hash;
  let solution = 0;
  do {
    hash = await sha512(challenge + ++solution);
  } while(hash.substr(0, level) !== "0".repeat(level));
  return solution;
}

4. 服务端 Python 校验实现

4. Python Implementation

在后端，我们可以将答案校验逻辑以及前端 JavaScript 求解器模板的组装封装进一个清爽优雅的 Python 类中：

On the back end, we can encapsulate the validation and JavaScript template delivery inside a clean Python class:

import hashlib

class ProofOfWork:
    def __init__(self, level):
        self.level = level

    def validate_solution(self, challenge, solution):
        return hashlib.sha512(
            (challenge + solution).encode()
        ).hexdigest().startswith('0' * self.level)

    @staticmethod
    def get_js_solver():
        return '''
            async function sha512(message) {
              const encoder = new TextEncoder();
              const data = encoder.encode(message);
              const hash = await window.crypto.subtle.digest("SHA-512", data);
              return new Uint8Array(hash).toHex();
            }

              let hash;
              let solution = 0;
              do {
                hash = await sha512(challenge + ++solution);
              } while(hash.substr(0, level) !== "0".repeat(level));
              return solution;
            }
        '''

5. Flask 与 WTForms 深度集成

5. Flask and WTForms Integration

架构设计原理

Design Architecture

  1. 隐藏表单字段：表单中包含一个专门用于存放工作量证明求解答案的隐藏字段 (hidden field)；
  2. 动态获取挑战：当用户点击 Submit (提交) 按钮时，自定义事件监听器会先拦截提交行为 (e.preventDefault())，将提交按钮置灰禁用，随后向服务端发送异步请求 (/_challenge) 获取一个全新的挑战 Token；
  3. 浏览器本地求解：客户端 JavaScript 求解器利用获取到的挑战 Token 与目标难度等级在本地极速运算，并将算出的答案填入隐藏字段；
  4. 服务端无缝校验：表单恢复正常提交。后端从用户 Session 中提取原始挑战并校验提交上来的计算答案。
  1. Hidden Field: The form includes a hidden field dedicated to the proof-of-work solution.
  2. Dynamic Challenge Request: When the user clicks Submit, the custom event handler intercepts the submission (e.preventDefault()), disables the submit button, and fetches a fresh challenge token from the server (/_challenge).
  3. Browser Solving: The JavaScript solver runs locally using the fetched challenge and target difficulty level, writing the answer to the hidden field.
  4. Server Verification: The form submits normally. The back end extracts the challenge from the user session and validates the submitted answer.

安全设计考量

Security Considerations

  • Session 安全存储：挑战 Token 必须妥善保存在具备密码学签名的客户端 Session Cookie（或服务端 Session）中，以防攻击者篡改或伪造挑战内容；
  • 防范重放攻击：每个挑战 Token 在存入 Session 时都会被赋予一个极短的过期时间戳（例如 15 到 60 秒），一旦过期或被使用即刻失效，从根本上杜绝重复使用已知答案重放提交的可能。
  • Session Storage: Challenges are stored in cryptographically signed client-side session cookies (or server-side sessions) to prevent users from tampering with or overriding challenges.
  • Replay Attack Prevention: Each challenge is assigned a short expiration timestamp (e.g., 15–60 seconds) stored in the session, rendering reused challenges invalid.

Challenge Generator Endpoint

from secrets import token_hex
from time import time
from flask import session

@app.route('/_challenge')
def _challenge():
    session['_ch'] = token_hex()
    session['_chexp'] = time() + 15
    return {'challenge': session['_ch']}

自定义 WTForms 校验器与渲染挂件

Custom WTForms Validator & Widget

from time import time
from wtforms.validators import ValidationError
from flask import session
from wtforms.widgets import html_params
from markupsafe import Markup
from wtforms import Field

class ProofOfWorkValidator:
    def __init__(self, message='Verification failed'):
        self.message = message

    def __call__(self, form, field):
        if time() <= session.pop('_chexp', 0):
            pow = ProofOfWork(field.level)
            challenge = session.pop('_ch', '')
            if field.data and pow.validate_solution(challenge, field.data):
                return True
        raise ValidationError(self.message)

class ProofOfWorkWidget:
    def __call__(self, field, error=None, **kwargs):
        kwargs.setdefault('id', field.id)
        kwargs.setdefault('name', field.name)
        attributes = html_params(**kwargs)
        return Markup(f'''
            <input {attributes} type="hidden" value="">
            <script>
              {ProofOfWork.get_js_solver()}
              document.addEventListener('DOMContentLoaded', () => {{
                const field = document.getElementById('{field.name}');
                const form = field.form;
                form.addEventListener('submit', async (e) => {{
                  e.preventDefault();
                  e.submitter.disabled = true;
                  const response = await fetch('/_challenge');
                  if (response.ok) {{
                    const challenge = (await response.json())['challenge'];
                    field.value = await solve(challenge, {field.level});
                  }}
                  HTMLFormElement.prototype.submit.call(form);
                }});
              }});
            </script>
            ''')

class ProofOfWorkField(Field):
    widget = ProofOfWorkWidget()

    def __init__(self, level, label='', validators=None, **kwargs):
        self.level = level
        validators = validators or [ProofOfWorkValidator()]
        super().__init__(label, validators, **kwargs)

from markupsafe import Markup

app.config['SECRET_KEY'] = 'top-secret!'

class TestForm(FlaskForm):
    name = StringField()
    challenge = ProofOfWorkField(level=4)

@app.route('/', methods=['GET', 'POST'])
def index():
    form = TestForm()
    name = None

7. Testing Your Protection

对于正常的人类用户而言，在点击提交时，只会在浏览器快速求解的瞬间感受到极其短暂且几乎微不可察的停顿（通常在 1 秒以内），体验完全自然流畅。

Legitimate users will experience only a minor, almost imperceptible pause upon clicking submit while the browser computes the solution.

而如果恶意垃圾机器人企图绕过真实浏览器，直接使用自动化工具（例如 curl 等脚本）向后端发起高频批量请求，其提交将直接触发校验失败而被严加拦截：

If a spam bot attempts to bypass the browser using automated tools (like curl), the request will fail validation:

curl -X POST http://localhost:5000/ -H "Content-Type: application/x-www-form-urlencoded" -d "name=foo&challenge=dont-know"
