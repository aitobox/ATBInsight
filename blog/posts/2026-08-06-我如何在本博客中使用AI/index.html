我如何在本博客中使用 AI

文章背景与核心概要

受 LessWrong 相关文章启发，作者详细阐述了在其个人技术博客中应用 AI 的核心原则与具体工作流。博客秉承“在公共场合学习”的理念，坚持所有文章文本与核心学习代码均由人工亲自编写，而将 AI 定位为辅助工具。AI 被广泛应用于创意构思、橡胶鸭调试、代码审查以及多模型编辑协同审查，但明确拒绝让 AI 代理全盘代劳，以保持低层探索的乐趣与学习摩擦感。

概要： 受一篇类似的 LessSword 文章 启发，本文阐述了本博客如何使用 AI。核心理念非常简单：AI 负责发现问题，我亲自动手解决。 虽然文本和核心学习代码严格由人工生成，以保持“公开学习”的精神，但 AI 在构思、代码审查、多阶段编辑反馈以及处理样板任务中发挥着强有力的支持作用。

Summary: Inspired by a similar LessSword post, this article outlines how AI is utilized on this blog. The core philosophy is simple: AIs identify problems, and I fix them myself. While text and core learning code are strictly human-generated to preserve the "learn in public" ethos, AI plays a heavy supporting role in ideation, code review, multi-stage editorial feedback, and handling boilerplate tasks.

创意构思与运行实验

每篇文章都基于原创想法和动手实践。对于大型编程项目（比如从零构建和训练 GPT-2），我会保持与 ChatGPT 或 Claude 的长期对话。因为这些项目的真正价值在于个人的学习过程，所以我采取了深思熟虑的措施来防止 AI 替我思考：

Every post is based on original ideas and hands-on work. For large-scale coding projects (like building and training GPT-2 from scratch), I maintain ongoing chat sessions with ChatGPT or Claude. Because the true value of these projects lies in the personal learning process, I take deliberate steps to prevent AI from doing my thinking:

  • 橡胶鸭模式： 当 AI 开始解释本应由我自己去发现的概念时，我会跳过阅读，直接滚动到输入框，引导它扮演小黄鸭调试的角色。

    • Rubber Duck Mode: When an AI starts explaining concepts I should discover myself, I skip reading, scroll straight to the input field, and redirect it into a rubber duck debugging role.

  • 代码审查： 对于复杂且相互依赖的项目，我会将代码粘贴到对话中以检查 bug。我的严格指令是：指出缺陷，但不要编写修复代码。

    • Code Review: For complex, interdependent projects, I will paste code into a chat session to check for bugs. My strict instruction: point out the flaws, but do not write the fixes.

编辑委员会

一旦我根据详细的项目笔记写完草稿，它就会进入一个多阶段的 AI 编辑流水线，旨在捕捉逻辑漏洞、技术错误和表达清晰度问题，同时绝不重写我的文字。

Once I finish drafting a post based on my detailed project notes, it goes through a multi-stage AI editorial pipeline designed to catch logical gaps, technical errors, and clarity issues without ever rewriting my words.

  1. Claude（第一轮）： 我将草稿粘贴到与 Claude 的新对话中。它会检查技术错误、遗漏步骤、过度解释和语法错误。

    1. Claude (First Pass): I paste the draft into a fresh chat with Claude. It looks for technical errors, missing steps, over-explanations, and grammatical mistakes.

  2. ChatGPT（第二轮）： 接下来是 ChatGPT，它要挑剔得多。它会检查参考链接（常常能捕获我训练代码中的隐蔽 bug），并指出与严谨技术术语相冲突的比喻。

    1. ChatGPT (Second Pass): Next comes ChatGPT, which is far more pernickety. It checks supporting links (often catching subtle bugs in my training code) and flags metaphors that clash with rigorous technical terminology.

  3. 多模型阵容： 最后，我会将草稿发送给轮换的其他大语言模型阵营（目前包括 DeepSeek、Grok、GLM-5.2 和 Kimi K3），以捕获前两者遗漏的内容，并跟进最新模型的性能表现。

    1. The Multi-Model Cast: Finally, I run the draft through a rotating cast of other LLMs (currently DeepSeek, Grok, GLM-5.2, and Kimi K3) to catch anything the first two missed and to stay updated on model capabilities.

  4. 人工最终润色： 我会在私人测试网站上进行最后通读——最好是在晚餐和一杯葡萄酒之后——以润色文风、消除过于正式的语言，并将可读性提升至最高。

    1. Final Human Polish: I do a final read-through on a private staging site—ideally after dinner and a glass of wine—to smooth out the prose, remove overly formal language, and maximize readability.

整个过程耗时从短篇博客的 30 分钟到大型专题文章的数小时不等。

The entire process takes anywhere from 30 minutes for a short post to a couple of hours for a major write-up.

AI 编程策略

我对编程的原则与对写作的原则如出一辙：如果通过编写代码能够有所收获，我就亲自手写。

My rule for coding mirrors my rule for writing: If I would learn something by writing the code, I write it by hand.

  • 亲力亲为： 核心概念和逻辑始终手动实现。

    • Hands-on: Core concepts and logic are always implemented manually.

  • 任务下放： 没有任何教育价值的样板任务——例如使用 matplotlib 绘制损失曲线，或构建炫酷的 JavaScript 参数可视化工具——都会交给 AI 处理（不过只要代码片段是由 AI 生成的，我总会明确披露）。

    • Delegated: Boilerplate tasks that offer no educational value—such as plotting loss curves with matplotlib or building a fancy JavaScript parameter visualizer—are handed off to AI (though I always explicitly disclose when a snippet is AI-generated).

  • 摩擦力控制： 为了避免被失控的范围所困扰，我总是通过标准聊天界面请求博客代码，而不是使用像 Claude Code 或 Codex 这样的 Agent 系统。

    • Friction Control: To avoid getting bogged down by runaway scope, I always request blog code through standard chat interfaces rather than using agentic systems like Claude Code or Codex.

拥抱 Agent，但暂不用于本博客

虽然在日常生活管理和目标导向型项目中我高度依赖 OpenClaw、Codex 和 Claude Code 等 Agent 工具，但它们目前还不属于本博客。

While I rely heavily on agentic tools like OpenClaw, Codex, and Claude Code for general life management and goal-oriented projects, they don't belong on this blog yet.

因为本博客的目的是记录动手实践、底层探索的学习过程（例如从零开始理解大语言模型的工作原理），过度自动化会违背这一初衷。一旦我拥有了扎实的基础并希望专注于更宏观的技术勾勒，未来情况可能会发生变化，但就目前而言：

Because the purpose of this blog is to document hands-on, low-level learning (e.g., understanding how LLMs work from the ground up), heavy automation would defeat the purpose. That may change in the future once I have a solid foundation and wish to focus on broader strokes, but for now:

本博客中的每一个字[^3]以及几乎每一行代码都是手写的——即使我需要一个 AI 委员会来让我保持在正轨上并维持基本的连贯性。

Every word[^3] and almost every line of code on this blog is written by hand—even if I need a committee of AIs to keep me on track and borderline coherent.
