探索 Linux 上 Go 1.27 程序的内存映射布局

文章背景与核心概要

本文基于 64 位 x86 Ubuntu 26.04 LTS 环境下的 Go 1.27rc2 版本，深入剖析了一个极简 Go 程序在 Linux 系统中的虚拟内存布局。利用 Go 运行时最新的诊断能力与 Linux 内核特性，文章逐一展示了程序二进制代码段、Go 堆区随机化分配、运行时内部元数据空间、页面分配器结构以及系统级映射（如 vdso、vvar 等）的详细视图。同时，文章还介绍了如何通过配置 decoratemappings=1 和依赖 Linux 内核 CONFIG_ANON_VMA_NAME 功能来开启带注释的内存映射分析。

1. 测试程序

1. The Test Program

为了干净地检查内存行为，我们使用一个极简的无限循环 Go 程序：

To examine memory behavior cleanly, we use a minimal, infinitely looping Go program:

package main

func main() {
    var i uint64
    for {
        i++
    }
}

注意： 请确保您的 go.mod 指定了 go 1.25 或更高版本。当在兼容的 Linux 发行版上运行时，该程序会公开一个内容丰富的 /proc/<pid>/maps 文件，详细展示虚拟内存布局。

Note: Ensure your go.mod specifies go 1.25 or higher. When run on a compatible Linux distribution, this exposes a rich /proc/<pid>/maps file detailing the virtual memory layout.

2. 程序二进制文件与数据段

2. Program Binary and Data Segments

地址空间中的最前端是程序的机器代码、只读数据、已初始化的变量以及零值数据区（bss）：

First in the address space are the program's machine code, read-only data, initialized variables, and zeroed data (bss) space:

00400000          504K r-xp   memdemo
0047e000          656K r--p   memdemo
00522000           32K rw-p   memdemo
0052a000          212K rw-p
  • 连续性： 从 0x00400000 到 0x0055f000 连续延伸。
  • 权限标志： r（读）、w（写）、x（执行）以及 p（私有、写时复制）。
  • 对比： 与 Go 1.11 (2018) 相比，二进制文件本身有所增大，这主要是由于隐式运行时包的扩展所致。
  • Contiguity: Spans continuously from 0x00400000 to 0x0055f000.
  • Flags: r (read), w (write), x (execute), and p (private, copy-on-write).
  • Comparison: Compared to Go 1.11 (2018), the binary itself has grown, largely due to expanded implicit runtime packages.

3. Go 堆区 (Go Heap)

3. The Go Heap

紧随其后的是 Go 主堆区，包含其初始预留的 64 MB arena 空间：

Next is the main Go heap, featuring its initial 64 MB arena reservation:

d75e4000000     12288K ---p  [anon: Go: heap reservation]
d75e4c00000      4096K rw-p  [anon: Go: heap]
d75e5000000     49152K ---p  [anon: Go: heap reservation]
  • 布局： 从 0xd75e4000000 到 0xd75e8000000 连续分布。其中仅有 4 MB 的块处于活跃分配状态；其余部分仍为预留空间。
  • 随机化： 自 Go 1.26 起，在 64 位平台上通过 RandomizedHeapBase64 实验特性，堆基地址随机化已成为默认设置。
  • Layout: Spans contiguously from 0xd75e4000000 to 0xd75e8000000. Only a 4 MB chunk is actively allocated; the rest remains reserved space.
  • Randomization: Since Go 1.26, randomizing the heap base address is the default on 64-bit platforms via the RandomizedHeapBase64 experiment.

4. Go 内部内存分配

4. Go Internal Allocations

Go 为其内部运行时机制预留了相当大量的虚拟地址空间：

Go allocates a substantial amount of reserved address space for its internal runtime mechanisms:

7b3b57e1c000      512K rw-p  [anon: Go: immortal metadata]
7b3b57e9c000       64K rw-p  [anon: Go: gc bits]

7b3b5805b000        4K rw-p  [anon: Go: page alloc]
7b3b5805c000      456K ---p  [anon: Go: page summary]
7b3b580ce000      128K rw-p  [anon: Go: page alloc]
7b3b580ee000      256K rw-p  [anon: Go: immortal metadata]
  • 规模： 该区域从 0x7b3b11460000 延伸至 0x7b3b5812e000（跨越约 1.1 GB 的虚拟地址空间），不过绝大部分被标记为 ---p（不可访问）。
  • 实际用量： 在这些预留空间中，仅有约 36.5 MB 被赋予读写权限并进行实际分配。
  • 主要组成部分：
  • 页分配与摘要 (Page allocation & summaries)： 由 runtime/mpagealloc.go 以及 mpagealloc_64bit.go 管理。
  • 回收索引 (Scavenge Index)： 与 runtime/mgcscavenge.go 中的内存回收（scavenging）逻辑关联。
  • 堆索引 (Heap Index)： 实现于 runtime/malloc.go 中的 L2 arena 映射表。
  • Scale: This block runs from 0x7b3b11460000 to 0x7b3b5812e000 (~1.1 GB of virtual address space), though the vast majority is marked ---p (inaccessible).
  • Actual Usage: Only ~36.5 MB of this reserved space is actively allocated with read/write permissions.
  • Source Components:
  • Page allocation & summaries: Managed via runtime/mpagealloc.go and mpagealloc_64bit.go.
  • Scavenge Index: Linked to memory scavenging in runtime/mgcscavenge.go.
  • Heap Index: L2 arena maps implemented in runtime/malloc.go.

5. 系统、栈与遗留映射

5. System, Stack, and Legacy Mappings

内存映射的尾部是内核提供和栈相关的区域：

Rounding out the memory map are kernel-provided and stack areas:

7b3b5812e000       16K r--p  [vvar]
7b3b58132000        8K r--p  [vvar_vclock]
7b3b58134000        8K r-xp  [vdso]
7ffc60b8f000      136K rw-p  [stack]
ffffffffff600000    4K --xp  [vsyscall]
  • vdso： 映射到进程空间的内核系统调用加速区。
  • Stack： exec() 时由内核分配的主进程栈。
  • Vsyscall： 遗留的内核接口区域。
  • vdso: Kernel system call acceleration mapped into the process space.
  • Stack: The primary process stack allocated by the kernel upon exec().
  • Vsyscall: A legacy kernel interface area.

6. 开启内存映射描述注释 (decoratemappings)

6. Enabling Memory Map Decoration (decoratemappings)

Go 利用 runtime/set_vma_name_linux.go 中的逻辑为这些内存区域标注名称。但要获取这些描述性名称，需要满足以下特定条件：

Go annotates these memory regions using logic found in runtime/set_vma_name_linux.go. However, getting these descriptive names requires meeting specific criteria:

  1. Go 版本要求： 使用 Go 1.25 或更新版本构建，且 go.mod 中指定了 go 1.25（或更高）。（如果 go.mod 指定了较旧版本，Go 默认会使用 decoratemappings=0。）
  2. 环境变量设置： 显式确保 $GODEBUG 包含 decoratemappings=1。
  3. 内核支持： 宿主 Linux 内核在编译时必须启用 CONFIG_ANON_VMA_NAME。
  4. Ubuntu 自 22.04 LTS 版本起已默认启用该配置。
  5. Fedora 通常在发布时禁用该选项（这会导致具有相同权限但不同描述名称的相邻虚拟内存区域无法合并）。
  1. Go Version: Built with Go 1.25 or newer, with go 1.25 (or higher) specified in go.mod. (If an older version is in go.mod, Go defaults to decoratemappings=0.)
  2. Environment Variable: Explicitly ensure $GODEBUG includes decoratemappings=1.
  3. Kernel Support: The host Linux kernel must be compiled with CONFIG_ANON_VMA_NAME enabled.
  4. Ubuntu has enabled this since at least version 22.04 LTS.
  5. Fedora typically ships with this option disabled (which prevents merging adjacent virtual memory areas with identical permissions but different descriptive names).
