探秘 Linux 下 Go 1.27 程序的内存映射布局

文章背景与核心概要

在 64 位 Ubuntu Linux 环境下，Go 语言通过其运行时（runtime）机制对虚拟内存进行管理。本文基于最新的 Go 1.27rc2 深入探究了一个极简 Go 程序的底层虚拟内存布局（/proc/<pid>/maps）。文章利用现代 Go 引入的匿名内存区域标注功能（decoratemappings），细致拆解了 Go 机器码、堆内存分配、内部运行时元数据、页分配器以及栈空间分布。通过具体数据与对比，清晰阐明了虚拟内存保留空间与实际物理内存占用之间的本质区别。

导言

Introduction

多年前，我曾写过一篇深入分析 Go 1.11 简单程序的 Linux 操作系统内存占用 的文章。最近，我使用 Go 1.27rc2 重新探讨了这个话题，因为现代版本的 Go 能够展现出更多有关其内部内存使用情况的信息。

Many years ago, I wrote a deep dive into the Linux OS memory use of a simple Go 1.11 program. Recently, I returned to this topic using Go 1.27rc2, because modern versions of Go can reveal significantly more information about their internal memory usage.

为了展示这一点，我们使用下面这个极其简单的程序：

To demonstrate, let's use this extremely simple program:

package main

func main() {
    var i uint64
    for {
        i++
    }
}

注意：你需要将 go.mod 文件中的 go 版本设置为 1.25 或更高版本。

Note: You will want to set go 1.25 or higher in your go.mod file.

当在合适的 Linux 发行版上运行此程序时，它会生成一个包含丰富信息的 /proc/<pid>/maps 文件。在下文中，我将该文件按逻辑划分为不同的区域，并重新格式化了各项记录，使用内存块大小代替起始与结束内存地址。所有数据均是在 64 位 x86 Ubuntu 26.04 LTS 服务器上采集的。

When running this on a suitable Linux distribution, the program generates an informative /proc/<pid>/maps file. Below, I have broken this file down into logical sections and reformatted the entries to show block sizes instead of start-to-end memory addresses. All data was captured on a 64-bit x86 Ubuntu 26.04 LTS server.

1. 程序二进制与数据段

1. Program Binary and Data Segments

首先，我们看到的是程序的机器码、只读数据、已初始化的变量以及清零的数据空间（bss）：

First, we see the program's machine code, read-only data, initialized variables, and zeroed data (bss) space:

00400000          504K r-xp   memdemo
0047e000          656K r--p   memdemo
00522000           32K rw-p   memdemo
0052a000          212K rw-p

这些段是连续的，跨越 0x00400000 到 0x0055f000 的地址范围。 * r、w 和 x 标志分别代表只读、可写和可执行权限。 * p 标志表示这些映射是写时复制（私有/private）。(至于为什么代码段和只读数据段被映射为 p，这超出了本文的讨论范围)。

These segments are contiguous, spanning from 0x00400000 to 0x0055f000. * The r, w, and x flags stand for read, write, and execute permissions, respectively. * The p flag indicates that these mappings are copy-on-write (private). (The exact reason why the code and read-only data sections are mapped as p is beyond the scope of this discussion).

与 2018 年的 Go 1.11 版本 相比，基础程序的占用空间有所增长，这很可能是因为默认隐式引入的运行时包发生了扩张。

Comparing this to the Go 1.11 version from 2018, the base program footprint has grown, likely due to expansions in the runtime packages implicitly pulled in by default.

2. Go 堆内存

2. The Go Heap

接下来是 Go 主堆内存，它由初始预留的 64 MB arena（区域）锚定。对于这个极简程序而言，实际上仅分配了 4 MB 的块供使用，其余部分仍属于预留空间：

Next is the main Go heap, anchored by its initial 64 MB arena reservation. For this trivial program, only a 4 MB chunk has actually been allocated for use, while the rest remains reserved space:

d75e4000000     12288K ---p  [anon: Go: heap reservation]
d75e4c00000      4096K rw-p  [anon: Go: heap]
d75e5000000     49152K ---p  [anon: Go: heap reservation]

这形成了一个从 0xd75e4000000 到 0xd75e8000000 的连续内存块，非常直观地展现了其 64 MB 的预留尺寸。

This forms a contiguous block from 0xd75e4000000 to 0xd75e8000000, cleanly illustrating its 64 MB size.

历史上，Go 堆内存的位置是固定的，但自 Go 1.26 起，在 64 位平台上随机化堆基地址已成为默认设置。虽然在技术层面这仍属于一个持续存在的 Go 实验特性（来源），在 internal/goexperiment 中被追踪为 RandomizedHeapBase64，但如果需要，理论上是可以将其禁用的。

Historically, the Go heap's location was fixed, but since Go 1.26, randomizing the heap base address is the default on 64-bit platforms. While still technically a lingering Go experiment (via) tracked as RandomizedHeapBase64 in internal/goexperiment, it can theoretically be disabled if needed.

3. Go Internal Allocations

Next comes a large assortment of internal Go runtime allocations stacked consecutively:

7b3b250ec000   234576K ---p  [anon: Go: scavenge index]

7b3b5805c000      456K ---p  [anon: Go: page summary]

该区域从 0x7b3b11460000 延伸至 0x7b3b5812e000。其中最大的几个块被标记为不可访问（---p，即不具备读、写或可执行权限）。总共占用了略高于 1 GB 的虚拟地址空间（约 1,159,992 KB）。

This region spans from 0x7b3b11460000 to 0x7b3b5812e000. The largest blocks are marked as inaccessible (---p, possessing no read, write, or execute permissions). In total, this accounts for just over 1 GB of virtual address space (~1,159,992 KB).

Go 源代码中的这些名称源自何处？ * 内存页分配与摘要（Page allocation & summaries）： 在 src/runtime/mpagealloc.go 和 src/runtime/mpagealloc_64bit.go 中管理。 * 物理内存回收索引（Scavenge index）： 位于 src/runtime/mgcscavenge.go（与页分配密切耦合）。 * 堆索引（Heap index）： 在 src/runtime/malloc.go 中定义为“L2 arena map”的一部分。

Where do these names come from in the Go source code? * Page allocation & summaries: Managed across src/runtime/mpagealloc.go and src/runtime/mpagealloc_64bit.go. * Scavenge index: Found in src/runtime/mgcscavenge.go (tightly coupled with page allocation). * Heap index: Defined in src/runtime/malloc.go as part of the "L2 arena map."

虽然这预留的虚拟地址空间显著多于 2018 年 Go 1.11 的用量，但实际上只有约 36,572 KB 被分配为具有读/写权限的可访问内存——与 Go 1.11 相比并没有大幅增加。在受限环境中，仅预留虚拟地址空间与实际拥有物理内存支持之间的区别至关重要。

While this reserves significantly more virtual address space than Go 1.11 used in 2018, only about 36,572 KB is actually allocated as accessible memory with read/write permissions—not drastically higher than Go 1.11. The distinction between merely reserving virtual address space and actually backing it with physical memory can be critical in constrained environments.

(注：该输出并未显示有多少内存已被实际访问并驻留在物理 RAM 或交换空间（swap）中；程序通常会建立读写内存映射，但并不会立即访问其中的每一个页面)。

(Note: This output does not show how much of that memory has actually been touched and resides in physical RAM or swap; programs frequently set up read/write memory mappings without immediately accessing every page).

4. Kernel and System Mappings

在 Go 专属的内存段之后，我们可以看到标准的系统内存分配：

Following the Go-specific segments, we find standard system allocations:

The vDSO

内核将虚拟动态共享对象（vdso）映射到进程的地址空间中，范围从 0x7b3b5812e000 到 0x7b3b58136000：

The kernel maps the virtual dynamic shared object (vdso) into the process's address space from 0x7b3b5812e000 to 0x7b3b58136000:

7b3b58132000        8K r--p  [vvar_vclock]

启用内存标注（decoratemappings）

Enabling Memory Annotations (decoratemappings)

在兼容的 Linux 系统上，Go 使用位于 src/runtime/set_vma_name_linux.go 中的逻辑来命名这些内存区域。

On compatible Linux systems, Go names these memory regions using logic found in src/runtime/set_vma_name_linux.go.

该行为由 $GODEBUG 中的 decoratemappings 选项控制，该选项引入于 Go 1.25，并且在 Go 1.25 及更高版本中默认开启。然而，仅仅使用现代的 Go 工具链编译是不够的：如果你的 go.mod 指定了较旧的 Go 版本，除非显式覆盖，否则 Go 默认会将 decoratemappings 设置为 0。

This behavior is controlled by the decoratemappings option in $GODEBUG, which was introduced in Go 1.25 and defaults to enabled for Go 1.25 and later. However, simply compiling with a modern Go toolchain isn't enough: if your go.mod specifies an older Go version, Go will default to decoratemappings=0 unless explicitly overridden.

具名内存映射的要求：

Requirements for Named Memory Mappings:

  1. 工具链版本： 使用 Go 1.25+ 进行构建。
  2. 配置说明： 确保 go.mod 中指定的 Go 版本为 1.25+，或者在运行时显式传递 GODEBUG=decoratemappings=1。
  3. 内核支持： Linux 内核必须启用 CONFIG_ANON_VMA_NAME 配置选项编译。
  4. Ubuntu 至少从 22.04 LTS 版本开始就已经默认启用了该选项。
  5. 相比之下，Fedora 在历史上则一直保持禁用状态。
  1. Toolchain Version: Build with Go 1.25+.
  2. Configuration: Ensure your go.mod specifies Go 1.25+ or explicitly pass GODEBUG=decoratemappings=1 at runtime.
  3. Kernel Support: The Linux kernel must be compiled with the CONFIG_ANON_VMA_NAME configuration option enabled.
  4. Ubuntu has enabled this since at least version 22.04 LTS.
  5. Fedora, by contrast, has historically left it disabled.

(注：反对启用 CONFIG_ANON_VMA_NAME 的主要理由是，它会阻止内核合并那些具有相同权限但带有不同名称的相邻虚拟内存区域。例如，在我们跟踪的输出中，位于 0x7b3b11460000 的前两个内存区域被分离开来，而如果激活了 decoratemappings=0，它们将被合并为一个单一内存块)。

(Note: The primary argument against enabling CONFIG_ANON_VMA_NAME is that it prevents the kernel from merging adjacent virtual memory areas that share identical permissions but carry different names. For instance, the first two memory areas at 0x7b3b11460000 in our trace are kept separate, whereas they would be collapsed into a single block if decoratemappings=0 was active).
