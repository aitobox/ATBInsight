Compiler Explorer 在 2026 年如何基于 AWS 运行

How Compiler Explorer Runs on AWS in 2026

在大语言模型（LLM）辅助下撰写。

Written with LLM assistance.

文章背景与核心概要

本文详细介绍了在线代码编译与汇编分析工具 Compiler Explorer（Godbolt）截至 2026 年在亚马逊云服务（AWS）上的底层架构与运维实践。全平台每月处理约 520 万次编译（年均约 7870 万次），支持 93 种编程语言和 6000 多个编译器版本。架构核心包含基于 CloudFront/WAF 的边缘分发与限流、基于 Spot 实例的多集群弹性伸缩，以及基于 CEFS（SquashFS + autofs）解决 NFS 文件系统高延迟的创新存储方案。在每月仅约 3600 美元（折合单次编译 0.0007 美元）的低成本下，该平台实现了高效、高可用且可持续的云端基础设施运行。

概要

Summary

这篇文章深入探讨了截至 2026 年 Compiler Explorer 在亚马逊云服务（AWS）上的最新架构运作方式。平台每月处理约 520 万次编译（每年约 7870 万次），涵盖 6,000 多个编译器和 93 种编程语言，运行在极具性价比、可扩展且具备弹性的云端基础设施之上。

This article provides an in-depth architectural update on how Compiler Explorer operates on Amazon Web Services (AWS) as of 2026. Processing roughly 5.2 million compilations a month (approx. 78.7 million annually) across more than 6,000 compilers and 93 languages, the platform runs on a cost-effective, scalable, and resilient cloud infrastructure.

关键架构组件包括： * 边缘与 CDN： AWS CloudFront 和 AWS WAF 负责全球内容交付，缓存静态资源（如 Monaco 代码编辑器），并管理简单速率限制。 * 计算集群： 一个 Application Load Balancer（应用负载均衡器）将传入流量分发给专门的 Auto Scaling 组（生产环境、Beta、暂存环境、Windows/MSVC、ARM64 Graviton 以及 GPU 集群）。生产环境高度依赖低成本的 EC2 Spot 实例。 * 存储与编译器： 为了解决包含数千个小头文件的 NFS 延迟问题，Compiler Explorer 使用了 CEFS——基于内容寻址、由 SquashFS 驱动的镜像，并通过 autofs 动态挂载。 * 夜间构建与 CI： 运行在 EC2 上的 GitHub Actions runner 每晚从头编译 94 个夜间构建目标。 * 成本与可持续性： 总运营成本维持在每月约 3,600 美元左右（单次编译约 0.0007 美元），大部分成本被 AWS 开源赞助额度、Patreon 赞助者和商业赞助商抵消。

Key architectural components include: * Edge & CDN: AWS CloudFront and AWS WAF handle global delivery, caching static assets (like the Monaco code editor), and managing simple rate limits. * Compute Fleets: An Application Load Balancer distributes incoming traffic to specialized Auto Scaling Groups (Production, Beta, Staging, Windows/MSVC, ARM64 Graviton, and GPU fleets). Production relies heavily on low-cost EC2 Spot Instances. * Storage & Compilers: To circumvent NFS latency with thousands of small header files, Compiler Explorer uses CEFS—content-addressed, SquashFS-backed images mounted dynamically via autofs. * Nightly Builds & CI: GitHub Actions runners on EC2 compile 94 nightly targets from scratch every night. * Cost & Sustainability: Total operating costs hover around \(3,600/month (~\)0.0007 per compilation), heavily offset by AWS open-source credits, Patreon backers, and commercial sponsors.

将代码传输至我们的服务器

Getting Your Code as Far as Our Servers

您的浏览器会与 Amazon 的 CDN 服务 CloudFront 进行通信。我们运行着两个独立的 CloudFront 分发站点。godbolt.org 前端的那个分发主要负责将请求转发给我们的负载均衡器，在返回过程中合理缓存并压缩数据[^brotli]。体积庞大的静态资源则存放在第二个分发站点 static.ce-cdn.net 背后的 S3 存储桶中：包括编译好的 JavaScript、图片和网页字体。其中占比最大的是 Monaco——来自 Visual Studio Code 的编辑器组件，正是它提供了语法高亮、波浪线错误提示等功能。对于只想要查看汇编指令的用户来说，要传输的 JavaScript 代码量相当大，因此在离用户近的地方进行缓存非常具有价值。

Your browser talks to CloudFront, Amazon's CDN. We run two separate CloudFront distributions. The one in front of godbolt.org mostly just hands requests on to our load balancer, caching what it sensibly can and compressing things on the way back out[^brotli]. The bulky static stuff lives in an S3 bucket behind a second distribution at static.ce-cdn.net: the compiled JavaScript, the images, the web fonts. Much the largest part of that is Monaco, the editor component out of Visual Studio Code, which is what gives you the syntax highlighting and the squiggly underlines and the rest of it. It's a lot of JavaScript to send someone who only wants to look at some assembly, so it's worth having it cached near them.

坐落在最前端的是负责速率限制的 WAF。我们的限流规则非常简单且上限非常高，主要是因为以前规则更严时经常误伤 C++ 培训班：整个教室的学生都处在技术大会同一个 NAT 出口 IP 后，看起来就像一个极度活跃的单 IP。我们本来可以采用更聪明的设备指纹技术，但提高限制额度更加省事，而且自那以后就再没出过问题。[^bans]

Sitting in front of that is WAF, doing our rate limiting. Our limits are very simple and very high, mostly because we used to be stricter and it kept catching C++ trainers: a whole classroom behind a conference's NAT looks like a single very keen IP address. We could probably do something cleverer with fingerprinting, but raising the limit was easier and it hasn't been a problem since.[^bans]

单个负载均衡器背后的众多集群

Rather a Lot of Fleets Behind One Load Balancer

在 CloudFront 后面是一个单一的 Application Load Balancer（应用负载均衡器）。它根据请求路径判断目标集群，然后挑选该集群中健康的一个实例进行请求转发。几乎绝大多数请求没有任何特殊前缀，直接打到 Production（生产）集群，绝大部分流量也都在这里被处理。/beta* 和 /staging* 分别分发至 Beta 和 Staging 集群。[^envs] /winprod* 去往运行 MSVC 的 Windows 实例集群，/aarch64prod* 去往原生运行 ARM 代码而非模拟运行的 Graviton 机器集群，而 /gpu* 则去往配备真实 NVIDIA 显卡的高性能机器集群。[^gpu]

Behind CloudFront is a single Application Load Balancer. It works out from the path which cluster a request is for, and then picks a healthy instance in that cluster to send it to. Almost everything has no special prefix at all and goes to the production fleet, which is where the overwhelming bulk of the traffic ends up. /beta* and /staging* go to the beta and staging fleets.[^envs] /winprod* goes to a fleet of Windows instances running MSVC, /aarch64prod* to Graviton machines that run ARM code natively rather than under emulation, and /gpu* to machines with real NVIDIA cards in them.[^gpu]

上述每一个集群都是一个 Auto Scaling 组，如今每个组都配置了双份：蓝组与绿组。进行部署时，我们拉起另一种颜色的集群，等待其通过健康检查，将负载均衡器的目标组指向它，并对旧集群进行优雅注销（drain）。如果新版本有问题，只需切换回原组即可。在采用这种机制之前，部署意味着使用我们的 ce 命令行工具对集群进行滚动重启，一次更新一个实例。这种做法虽然可行，但如果想要回滚有问题的发布，就意味着要再次将整个集群滚动重启回上一个版本，当网站刚刚挂掉时，这种恢复方式显得过于缓慢。

Each of those is an Auto Scaling Group, and these days each one is doubled up: a blue and a green. To deploy, we bring up the other colour, wait for it to go healthy, point the load balancer's target group at it and drain the old one. If it's wrong, we point it back. Before that, deploying meant a rolling restart of the fleet with our ce command line tool, one instance at a time. That worked well enough, but backing out a bad release meant rolling the whole fleet forward again onto the previous version, which is a bit slow when you've just broken the site.

伸缩逻辑本身很简单：我们只是尽量将平均 CPU 负载维持在某个阈值以下。我们探讨过更复杂的方案，但目前这个方案开箱即用支持得最好。[^queuescale]

The scaling itself is simple: we just try and keep the average CPU load below a threshold. We've kicked around more sophisticated ideas but this one is supported out of the box.[^queuescale]

租用别人不需要的计算资源

Renting the Bits Nobody Else Wants

生产集群几乎完全由 Spot 实例（竞价实例）组成——这些是未被使用的 EC2 空闲容量，以低廉的价格出售，前提是如果 AWS 顺位收回，可能会在 2 分钟前通知打断。相比按需实例，这为我们节省了 60-90% 的费用——对我们来说省下了一大笔资金。

The production fleet is almost entirely spot instances -- unused EC2 capacity, sold off cheap, on the understanding that you can be evicted at two minutes' notice. It's a 60-90% saving over on-demand -- quite a lot of money, for us.

我们之所以能这么做，是因为我们的单台实例本身并不承载状态。所有需要持久化保存的内容都存放在共享文件系统、S3 或 DynamoDB 中，因此某个实例突然消失仅仅意味着它会被新实例替换。我们跨 m5、m6、m7、r6 以及 i3/i4i 系列申请了 16 种不同的实例类型。配置的分配策略是 price-capacity-optimized——Amazon 用这种方式表达“挑选既便宜又最不容易被收回的实例”。在实际运行中，一旦某个实例被收回，弹性伸缩组就会感知到，并迅速启动一个全新的实例。

We can get away with that because our instances don't really matter. Everything that needs to survive lives on the shared filesystem, in S3 or in DynamoDB, so an instance that vanishes is just an instance that gets replaced. We ask for sixteen different instance types across the m5, m6, m7, r6 and i3/i4i families. The allocation strategy is price-capacity-optimized -- Amazon's way of saying "pick whichever of these is cheapest and least likely to get yanked". In practice we get evicted, the scaling group notices, and a new one turns up.

为什么编译器才是最难的部分

Why the Compilers Are the Hard Part

我们跨 93 种语言拥有约 6,000 个编译器条目[^double]，并且我们从不删除其中的任何一个。[^never] 某个版本的编译器一旦上线就会永久保留，这样当年 Stack Overflow 上展示 GCC 4.8 代码生成特性的回答在今天依然能够正常编译。这是我们对抗“链接腐败”（link rot）的方式，也意味着我们保留了海量的二进制文件。

We have around 6,000 compiler entries[^double] across 93 languages, and we never delete any of them.[^never] Once a compiler version goes up it stays up, so that Stack Overflow answer showing a GCC 4.8 codegen quirk still compiles today. It's our bit against link rot, and it does mean we hoard an awful lot of binaries.

所有这些文件都存放在 Amazon 的弹性 NFS 服务 EFS 上，而 NFS 是存在高延迟问题的。类 C 语言会引用极其庞大数量的微小头文件，因此最朴素的直接读取方案慢到了无法使用的地步。我们的解决办法听起来有些笨拙：为每个编译器构建一个 SquashFS 镜像，将镜像同样存储在 EFS 上，并使用回环设备（loopback）将其挂载。这样一来，操作系统内核会认为自己正在与本地块设备通信，从而正确地对数据块进行缓存，而不是每次读取都要跨建筑与远端服务器做网络校验。[^squash]

All of that lives on EFS, Amazon's elastic NFS, and NFS has latency. C-like languages pull in an enormous number of very small header files, so the naive version of this is unusably slow. Our fix, which sounds daft, is to build a SquashFS image per compiler, store the image also on EFS, and mount it through a loopback device. The kernel then thinks it's talking to a local block device and caches blocks properly instead of checking with a server in another building every time.[^squash]

这个方法起作用了，但它意味着每次开机都要挂载几千个镜像，这需要花上将近一分钟的时间，并导致数千个文件系统的元数据一直占用内核内存。这些缓存的元数据正是 SquashFS 性能击败 NFS 的核心原因，因此并不算浪费；问题在于任何单个实例在运行期间实际上只会触及这一小部分编译器，我们却为全部编译器占用的资源埋了单。我花了三年时间和多次放弃的尝试才修复这个问题，最终的方案是 CEFS：内容寻址的镜像，打包成约 20GB 大小的包，在首次有程序触及对应路径时由 autofs 按需挂载。这次迁移将我们的镜像数量从 2,182 个减少到 121 个，系统启动时间从 50 秒缩短到了 20 秒！不过自那以后镜像数又慢慢回升到了约 883 个，因为夜间构建会不断产生新镜像，而压缩整理只能打包已存在的镜像。在我写这篇文章时运行的一次垃圾回收清出了 111 个不再被任何地方引用的镜像，大小约为 63GiB。[^gc]

That worked, but it meant mounting a couple of thousand images at every boot, which took the best part of a minute and kept the metadata for thousands of filesystems resident in kernel memory. That cached metadata is a good chunk of why squashfs beats NFS in the first place, so it's not wasted as such; it's just that any one instance is only ever going to touch a handful of those compilers, so we were paying for all of it to use a fraction of it. It took me three years and several abandoned attempts to fix that, and the answer was CEFS: content-addressed images, packed into bundles of around 20GB, mounted on demand by autofs the first time something touches the path. The migration took us from 2,182 images down to 121, and OS startup from 50 seconds to 20! It's crept back up to around 883 since, because the nightly builds keep making new images and consolidation only packs down whatever is already there. A garbage collection while I was writing this turned up 111 images that nothing references any more, about 63GiB's worth.[^gc]

过去一年里，我们的存储占用也下降了很多，不过老实说我不太确定这在多大程度上要归功于 CEFS，又有多少是因为我终于删掉了旧的 squash 镜像：

Our storage has come down a lot over the year too, though I'm honestly not sure how much of that is CEFS and how much is me finally deleting the old squash images:

Aug/04 01:55 admin-node~ $ df -h

2.2T, where a year ago it was 3.9T. Still nowhere near 8 exabytes, mind.

每晚不停歇地构建编译器

Building Compilers All Night, Every Night

我们每晚都会从头构建大量编译器：GCC trunk、Clang trunk，以及用于反射、契约、协程和其他各种新奇特性的长尾实验分支。目前每晚有 94 个构建任务[^jobs]，高于一年前的 73 个和 2022 年的 33 个。

We build a pile of compilers from scratch every night: GCC trunk, Clang trunk, and a long tail of experimental branches for reflection, contracts, coroutines and all the other fun stuff. That's 94 nightly build jobs at the moment,[^jobs] up from 73 a year ago and 33 in 2022.

这些构建任务运行在搭建于 EC2 上的自托管 GitHub Actions runner 上，通过优秀的 terraform-aws-github-runner 按需拉起，上层的编译器构建编排系统则由我们自己开发。构建主线 LLVM 需要配置较高的机器和相当长的时间，当我们最初搭建这套系统时，GitHub 的托管 runner 根本无法满足需求。

Those run on our own GitHub Actions runners on EC2, spun up on demand with the excellent terraform-aws-github-runner, with all the compiler orchestration on top being ours. Building trunk LLVM wants a big machine and a decent chunk of time, and GitHub's hosted runners weren't up to it when we set this up.

每当有人请求我们添加新编译器而我们同意时，账单中上升的那部分开销就是由此产生的。[^stale]

This is the part of the bill that goes up every time somebody asks us for another compiler and we say yes.[^stale]

完成了一半的功能组件

The Bits That Are Half-Finished

我们已经构建但尚未完全上线的一个组件是 CE Router（CE 路由器）：这是一个小规模集群，其工作是决定某个编译请求应该在哪里执行，在 DynamoDB 中查找答案并将请求放入 SQS 队列，最终处理结果通过 API Gateway WebSocket 返回给您的浏览器。其目的是解耦“响应 HTTP 请求的机器”与“实际拥有并运行编译器的机器”。

One thing we've built but not finished rolling out is what we call the CE Router: a small fleet whose job is to decide where a compilation should happen, look the answer up in DynamoDB and drop the request on an SQS queue, with the result coming back to your browser over an API Gateway WebSocket. The point is to stop the machine that answers the HTTP request having to be the machine that owns the compiler.

该系统能够正常工作，但尚未承载生产环境流量：将编译请求送入该路由器的负载均衡器规则仍处于注释状态，我们正在渐进式迁移。今天您的编译请求依然会像过去一样，直接打到生产集群中的某台机器上。

It works, but it isn't carrying production traffic yet: the load balancer rules that would send compilations through it are still commented out, and we're migrating gradually. Your compile today still goes straight to a machine in the prod fleet, the way it always has.

不过，在构建它的过程中，我们发现了一个很棒的 AWS 坑点。API Gateway WebSocket 帧数据上限为 32KiB，而几乎任何非玩具级程序的汇编代码都大于这个尺寸；在另一个方向上，SQS 消息最大限制为 256KB，规模稍大的多文件项目就会轻松超标。因此在两个方向上，如果数据过大，我们都会将其塞入 S3 中，仅传输对应的键名（key）。

Building it did turn up a good AWS gotcha, though. API Gateway WebSocket frames top out at 32KiB, and the assembly for almost any non-trivial program is bigger than that; in the other direction SQS messages cap out at 256KB, which a decent-sized multi-file project will go past. So in both directions, if the thing is too big we shove it in S3 and send a key instead.

其他所有组件

Everything Else

一系列各司其职的其他辅助服务：

  • DynamoDB 用于存储短链接。您在演示 PPT 中引用的每一个 godbolt.org/z/... 链接都是表中的一行记录，目前已有数百万条记录。
  • S3 存放我们构建的编译器、静态资源、日志，以及每日过期的内容寻址编译缓存，因此第二个编译相同内容的用户可以免费直接获取缓存结果。
  • Lambda 处理各类杂项：Claude Explain 后端、夜间版本追踪，以及将 CloudWatch 报警推送到我们 Discord 的函数，这样就不用在凌晨 3 点震响我的手机了。
  • Route 53、ACM、CloudTrail、Backup 和 SES 属于基础设施管道。我平时不太需要操心它们。
  • CloudWatch 驱动自动伸缩触发器，不过对于实际监控面板，我们运行的是 Grafana、Prometheus 和 Loki。这些仪表盘都是公开的。

A scattering of other services doing one job each: * DynamoDB holds the short links. Every godbolt.org/z/... you've put in a slide deck is a row in a table, and there are a couple of million of them. * S3 holds the compilers we build, the static assets, the logs, and a daily-expiring content-addressable compilation cache, so the second person to compile the same thing gets it for free. * Lambda does the odd jobs: the Claude Explain backend, the nightly version tracking, and the one that pushes CloudWatch alarms into our Discord so it's not just my phone buzzing at 3am. * Route 53, ACM, CloudTrail, Backup and SES are the plumbing. I don't think about them much. * CloudWatch drives the auto-scaling triggers, though for actually looking at things we run Grafana, Prometheus and Loki. Those dashboards are public.

所有资源都部署在 us-east-1 区域。如果您在悉尼进行编译，您的代码数据绕了大半个地球，恐怕这种情况还会继续下去：跨区域同步好几个 TB 的编译器镜像绝对是一场可怕的噩梦。

Everything is in us-east-1. If you're compiling from Sydney your code goes a long way round, and I'm afraid it's going to keep doing that: keeping a couple of terabytes of compilers in sync across regions would be an absolute nightmare.

一些数据统计

Some Numbers

我们每次编译都会向 S3 记录一条高度匿名化的 JSON 日志，并在其上建有 Glue 表，因此在撰写本文时我专门进行了精确统计：7 月份共有 5,238,210 次编译，过去 12 个月累计达 7870 万次。整个一年的趋势都在缓慢下滑，比去年秋天顶峰时期下降了约三分之一。

We log a heavily anonymised JSON record to S3 for every compilation, with a Glue table over the top, so while writing this I went and counted them properly: 5,238,210 compilations in July, and 78.7 million over the last twelve months. It's been sliding gently all year, down about a third from last autumn's peak.

在那之前的一次大幅下滑（从 2024 年的每月 1400 万次掉下来），我至少能解释一半原因：2024 年采集中期，我们将输入代码后自动重新编译的默认延迟时间加倍了，从 750 毫秒增加到了 1500 毫秒，随后又改成了 2 秒。[^delay] 如果您在连续打字，将延迟加倍大约会让您产生的编译次数减半，而用户几乎感觉不到什么差异。然而最近的这波下降并不是这个原因造成的：它是在那很久之后（一年多之后）才开始的。

The big drop before that, from 2024's 14 million a month, I can at least half explain: in mid-2024 we doubled the default delay before we auto-recompile as you type, from 750ms to 1500ms, and then to 2 seconds.[^delay] If you type continuously, doubling that delay roughly halves the number of compilations you generate, without anybody noticing anything much. This latest slide isn't that, though: it started well over a year later.

因此我并没有一个确切的解释，也很难去追查原因，因为我们有意的不追踪用户身份：没有 cookie，没有任何能让我算出昨天有多少人使用过网站的东西。如果让我重新选择，我依然每次都会做同样的选择，但这也导致我有时只能盯着图表发愣。

So I don't really have a good explanation, and I can't easily go and find one, because we deliberately don't track who you are: no cookies, nothing that would let me tell you how many people used the site yesterday. I'd make that trade again every time, but it does leave me squinting at graphs occasionally.

我仍想改进的地方

Things I'd Still Like to Fix

部署流程比以前好了，但人工介入的程度还是比我希望的要多。[^discovery] CE Router 的迁移处于“快要搞定”状态已经有一段时间了……我依然遗憾当年最开始没有规划好 NFS 的目录结构，而是十年来一个编译器一个编译器地野蛮生长。另外，我们今年把所有东西都迁移到了 Ubuntu 24.04 上，这可不像听起来那样是个干净省心的小升级。[^relr]

Deployment is better than it was but there's still more hand-holding in it than I'd like.[^discovery] The CE Router migration has been "nearly done" for a while now... I still wish I'd laid out the NFS directory structure properly at the start instead of growing it one compiler at a time for a decade. And we moved everything to Ubuntu 24.04 this year, which was not the tidy little upgrade it sounds like.[^relr]

这里面没有什么特别高深的技术：就是一个负载均衡器，几个跑着廉价 Spot 实例的弹性伸缩组，一个网络文件系统，以及十年来积累下来的各种临时 Hack。但它确实一直在稳定运行，而且如今大多数时候都不需要有人去特别维护。对此我感到挺满意的。

None of this is especially clever: it's a load balancer, some scaling groups full of cheap spot instances, a network filesystem and a decade of accumulated hacks. It does keep working, though, and these days it mostly keeps working without anyone having to go and poke it. I'm pretty happy with that.

[^queuescale]: The obvious better signal is queue depth: how many compilations are actually waiting, rather than how busy the CPUs happen to look. We already have scaling policies written against ApproximateNumberOfMessagesVisible for some of the environments, and once the queue-based compilation path is carrying real traffic everywhere that's what we'd like to scale everything on.

[^never]: 几乎从不。极少数情况下某个实验性构建会被替换，而夜间构建按定义每次都会自我替换：今天的 GCC trunk 会静默替换掉昨天的。只有正式发布的版本才会永远保留。

[^never]: Nearly never, anyway. Very occasionally an experimental build gets replaced, and the nightly builds replace themselves by definition: today's GCC trunk quietly does away with yesterday's. It's the released versions that stay put forever.

[^gc]: 内容寻址至少使得判断变得很安全：一个没有任何东西链接的镜像绝对是未使用的，因此垃圾回收可以是自动化的，而不需要我盯着文件名希望不要删错。那 111 个镜像中有很大一部分是昨天的夜间构建，被今天的构建静默替代了。

[^gc]: Content addressing does at least make that safe to work out: an image that nothing links to is definitely unused, so the collection can be automatic rather than me squinting at filenames and hoping. A good chunk of those 111 will be yesterday's nightly builds, quietly superseded by today's.

[^double]: 如果询问 API，会显示为 6,157 个，但这稍微有些“水分”：它将同一个 GCC 分别计算为 C、C++、Fortran 等。按唯一名称计算，它是 4,291 个。去年 6 月对应的数据是 4,724 个和 81 种语言，因此我们依然保持着不错的增长，而且这几乎不需要我干预：大家不断带着我从未听说过的语言和可用的 PR 找过来。

[^double]: 6,157 if you ask the API, but that's cheating slightly: it counts the same GCC once for C, once for C++, once for Fortran and so on. Unique names, it's 4,291. Last June the equivalent numbers were 4,724 and 81 languages, so we're still growing pretty nicely, and almost none of that is me: folks keep turning up with a language I'd never heard of and a working PR.

[^squash]: 通常情况下，NFS 会在本地缓存数据，但它仍需通过属性缓存与服务器确认缓存的元数据是否最新。即使文件数据已缓存，您仍需支付网络延迟以检查其是否更改。通过回环挂载 SquashFS 镜像“洗掉”了 NFS 的属性：squashfs 驱动程序看到的是一个本地块设备，内核完全不知道这些缓存数据块的背后是一个理论上可能发生变化的 NFS 文件。对于不可变的编译器镜像来说，这是一个巨大的福音。

[^squash]: Normally NFS caches data locally, but it still validates that cached metadata is fresh with the server via attribute caching. Even when the file data is cached you pay the network latency to check it hasn't changed. Going via a loopback-mounted SquashFS image "launders" away the NFS-ness: the squashfs driver sees a local block device, and the kernel is blissfully unaware that behind those cached blocks is a file on NFS that could in theory change. For immutable compiler images this is a huge boon.

[^jobs]: 一个“任务”不代表一个编译器：有的构建单个东西，有的构建整个家族。构建任务在 UTC 零点启动并排队运行在我们的构建基础设施上，而一个独立的安装工作流在上午 5:30 运行，这两者互不知晓，因此有时我们会安装昨天的构建。这已经在优化列表上了。

[^jobs]: A "job" isn't a compiler: some build one thing, some build a whole family. The builds kick off at midnight UTC and queue on our build infrastructure, and a separate workflow installs at 5:30am, and the two still have no idea about each other, so sometimes we install yesterday's builds. It's on the list.

[^stale]: 我们在处理上并不愚蠢：在夜间构建运行之前，它会检查上游仓库在过去一周内是否有过 commit，如果没有任何变动，就会直接跳过构建。一个实验性分支在平静的一周里几乎不会消耗我们任何资源。

[^stale]: We're not completely daft about it: before a nightly build runs it checks whether any of the upstream repositories have had a commit in the last week, and if nothing's moved it skips the build entirely. A quiet week on some experimental branch costs us nothing much.

[^delay]: 如果想看详细细节，可以参考 #6669。最早改成了 1500 毫秒，然后有人尝试了 2 秒，接着被撤回，十天后又恢复成 2 秒。目前的默认值是 2000 毫秒。

[^delay]: #6669, if you want the gory details. It went out at 1500ms, then someone tried 2 seconds, then it got reverted, then it went back to 2 seconds ten days later. The current default is 2000ms.

[^percomp]: 高于一年前的 $0.00039 美元，并不是因为什么东西变贵了，而是因为编译总量下降了，而固定成本（所有那些存储以及每晚构建所有编译器）保持完全不变。

[^percomp]: Up from $0.00039 a year ago, and not because anything got dearer. The volume went down and the fixed costs -- all that storage, and building all those compilers every night -- stayed exactly where they were.

[^top10]: 我在 2014 年做过同样的统计，在当时的近 200 万次总编译中，试图找出我能否退役 GCC 4.4。那时的默认选项是 clang++ 3.0.6，占比 37%，因此即使其他一切都变了，榜单的分布形态并没有大变。我当时并没有退役 GCC 4.4，它到今天依然还在。

[^top10]: I did this same exercise back in 2014, out of nearly 2 million compiles in total, to work out whether I could retire GCC 4.4. The default then was clang++ 3.0.6 at 37%, so the shape of the list hasn't changed much even if everything else has. I didn't retire GCC 4.4, and it's still there.

[^discovery]: 主要在于我们的“编译器发现”步骤：在某个版本发布之前，我们会去询问机器上的每一个编译器它到底是什么以及它的自称，并将答案写入一个 JSON 文件供网站读取。这仍然是一个手动步骤并且偶尔会出故障，不过我觉得我在最近的一个 commit 中让它变得更加稳定了。我也在尝试使用 LLM “脚本”来辅助处理无法直接在代码中自动化的部分：这里有很多奇怪的边角情况需要处理，将所有这些情况都正确编码相当困难。

[^discovery]: Mainly it's our "compiler discovery" step: before a version goes out we go and ask every compiler on the machine what it actually is and what it calls itself, and write the answers to a JSON file the site then reads. It's still a manual step and it can occasionally fall over, though I think I've made it rather more stable in a recent commit. I'm also experimenting with using LLM "scripts" to help where I can't automate things directly in code: there are a lot of weird edge cases to handle and encoding all of them properly is tricky.

[^relr]: 现代 glibc 使用 SHT_RELR 重定位，这需要 binutils 2.38 或更高版本来进行链接，而我们有 29 个旧版 GCC 自带的 ld 早于该版本。我们尝试过从源码重新构建所有这些 GCC，但这引发了一连串 libsanitizer 不兼容问题，因此我们放弃了，改为在安装时将这些编译器的 ld 软链接到更新的版本。Partouf 后来对其中几个进行了彻底的重新构建。

[^relr]: Modern glibc uses SHT_RELR relocations, which need binutils 2.38 or newer to link against, and 29 of our older GCCs ship their own ld that predates that. We tried rebuilding them all from source, which cascaded into a wall of libsanitizer incompatibilities, so we gave up and settled for symlinking those compilers' ld to a newer one at install time instead. Partouf later rebuilt a couple of them properly.
